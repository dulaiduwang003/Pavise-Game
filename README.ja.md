## 性能は上がるのか

Pavise は性能を無から生み出すものではありません。CPU や GPU の上限を超えさせることもできません。

やっているのはもっと単純なことです。**ゲーム中、バックグラウンドのアプリや更新処理、アンチチートに取られていた分の性能をゲームに戻す。** CPU・ディスク・スケジューリングはゲームが優先で取り、使っていないバックグラウンドには一歩下がってもらう。ゲームを終了したら元に戻す。それだけです。

なので、バックグラウンドで色々動いていて CPU やディスクがよく取り合いになる PC ほど、カクつき・フレームタイムの安定性・1% Low の改善が見込めます（結果として平均 FPS も少し上がることがあります）。もともとクリーンな環境や、完全に GPU 律速のゲームでは、ほとんど変わりません。逆に設定を攻めすぎると、ゲーム・ボイスチャット・アンチチートで不具合が出ることもあります。競技モードは最初から一番攻めた設定なので、選ぶということはそのトレードオフを受け入れるということです。

一言でいうと、**Pavise は性能を作り出すのではなく、すでにある性能が邪魔されないようにするツール**です。効果は同じゲームの同じ場面で、オン・オフを比べて判断してください。

## これは何をするもの

ゲーム（あるいは守りたい任意のプログラム）の EXE かショートカットを対象ライブラリに追加すれば、Pavise はそれを認識します。動いている限り保護され、デスクトップに切り替えても最小化しても保護から外れません。

ランチャーによっては、本体を別の場所（一時フォルダなど）から実行します。Pavise はファイル名と 64bit / バージョンの接尾辞から本体を突き止めるので、指定したフォルダの中にいる必要はありません。

完全にローカルで動くツールです。サービスは入れず、データも一切送信しません。ゲームへのインジェクションもせず、メモリやファイルも触りません。変更したシステム設定とプロセス状態はすべて記録し、書き込み後に読み戻せる項目は必ず確認します——期待した値が読み戻せない項目は成功として扱いません。性能の変化はゲーム内ベンチマークや普段お使いのモニタリングツールでご自身で確認してください。

## 動作の仕組み

ゲームの判定はプロセス名だけでは行いません。追加された入口、インストールフォルダ内のプロセス同士の関係、ウィンドウの状態、前面かどうかを組み合わせて判断します。ランチャー・更新プログラム・クラッシュレポーター・アンチチートは役割で先に除外するため、たとえそれを選んでいてもゲーム本体としては扱いません。ランチャー経由で起動するゲーム（先にランチャーが動き、そこから本体が立ち上がるもの）は、一度確認できれば本体を記憶して次回から直接認識します。記憶したパスが無効になれば自動的に破棄されます。一度確定したセッションは、別のウィンドウに切り替えても失われません。

認識できたあとは、モードに従って処理します。

- **標準モード**：ウィンドウのないバックグラウンドをまず軽く抑え、リソースを取り続けるものだけを強く抑えます。使用中のプログラムには触れません。
- **競技モード**：ゲーム以外は即座にすべて抑えます。ウィンドウがあっても例外ではありません。触れないのは、現在前面にあるプログラムとその子プロセス、ゲーム一式、アンチチート、ネットワークアクセラレーター、許可リスト、他のアカウント、システム中核サービスだけです。
- **カスタムモード**：バックグラウンド抑制・サービス停止・ネットワーク・通知・リフレッシュレートを一つずつ選べます。抑制範囲と電源の強度だけ競技モード相当にすることもできます。

ゲーム本体には高い優先度、高い I/O と GPU スケジューリング優先度、そして CPU に合ったコアを割り当てます。バックグラウンドはモードに応じて優先度を下げるか、別のコアに移します。書き込みは可能な限り読み戻して確認し、失敗は成功として扱いません。

アンチチートと対戦中のゲームホスト（各地域のクライアントなど）は、どのモード・どの強度でも無条件に除外します。モードや設定の影響を受けません——抑制しても切断されるだけだからです。

復元は記録に基づきます。触れたプロセスごとに変更前の状態を保存し（PID と作成時刻も一緒に検証するので、別のプロセスに復元してしまうことはありません）、終了時にその通りに戻します。Pavise がクラッシュした場合も、次回起動時に続きから復元します。

## 主な機能

- 対象ライブラリ：EXE / LNK / Steam ショートカット、ドラッグ＆ドロップ、インストール済みゲームのワンクリックスキャン（Steam / Epic / GOG / Ubisoft / Riot / WeGame / Battle.net / Xbox / Microsoft Store のインストール記録を読み取り。ネットワークアクセラレーターをゲームとして提案することはありません）
- ゲーム本体を自動で見分けるため、ランチャーが保護を占有し続けることがありません。別フォルダで動く本体、同一フォルダのランチャープロセス（Mount & Blade II など）、ランチャー経由の起動（League of Legends など）にそれぞれ対応
- 前面から外れても最小化しても保護は続きます
- CPU 分割はメーカーを問いません。ハイブリッド構成・X3D・複数プロセッサグループに対応。6 コア以下では強制的に分割せず、8 コア以上で初めて少数のバックグラウンドコアを確保します
- システム診断ページ：この PC で何が使えるか、実測値はどうか、既に何が設定されているかを読み取りのみで確認し、結論ごとに根拠の等級（本機実測 / ベンチ実測 / 仕組み上明確 / 未検証）を明示します。NVIDIA はワンクリックで書き込み実測が可能
- 新しいバージョンは起動時に古いバージョンを引き継ぎます。古い方は自身の終了処理を通して完全に復元してから終了します——強制終了ではありません
- USB 割り込みの退避：4K/8K ポーリングマウスの割り込みをゲームのコアから逃がします
- League of Legends 専用機能：WeGame 経由の起動、精密なクリーンアップ、対戦中の完全ヘッドレス、独立した復旧ウォッチドッグ
- アンチチート抑制はベンダーごとにグループ分けし、各グループ 3 段階の強度。既定はすべて一番穏やかな段階
- 電源プラン、ネットワーク、MMCSS、Game DVR、通知、サービス停止はすべて復元可能
- NVIDIA 詳細設定：電源の最高パフォーマンス、フレームレート上限。元の値はスナップショットを保持し、オフにすれば復元
- 対戦前のスタンバイメモリ整理（既定オフ）と MPO の切り分けスイッチ
- 対戦ごとの成果を実行ログに記録：プレイ時間、抑制したバックグラウンドの数、それらが使った CPU の合計
- UI は簡体字中国語のみ。多言語の仕組みはコード内に残しています

## 安全境界

アンチチート、対戦中のゲームホストとそのフォルダ、Windows 中核サービス（ログオン、認証、デスクトップ合成、オーディオなど）、他のログインアカウント、そして Pavise 自身は、どのモード・どの強度でも抑制対象になりません。この線はどの設定でも変わりません。

競技級の強度でなければ、前面のプログラムとウィンドウを持つプログラムは、同名プロセスや子プロセスも含めて抑制されません。ブラウザや IDE のような複数プロセス構成のソフトで、UI の殻だけが守られる状態を避けるためです。競技級の強度（競技モード、またはカスタムでの個別有効化）では「ウィンドウがある」という除外条件が外れますが、現在前面にあるプログラムとその子プロセスは引き続き触れません。ネットワークアクセラレーターも常に除外されます。それ以外に守りたいものは許可リストに追加してください。

アンチチート抑制はもともと攻めた処理です。保護されたプログラムが変更を拒否したり、自分で元に戻したりすることがあります。その場合は失敗として記録し、復元情報を保持します。成功としては扱いません。

ログオフやシャットダウンの際は、再起動しても消えない変更（電源プラン、レジストリ系）を先に戻します。終了処理の時間が足りない場合に優先して守るのは、再起動でも自動的には直らない部分です。

## League of Legends 専用機能

WeGame はログインと起動だけを担当します。ロビーの準備完了を確認したあと、検証済みのインストールパスに基づいて WeGame と地域版の付加プロセスを正確に終了させます。対戦が始まるとクライアント自身のインターフェースでロビー画面を閉じ、対戦後は独立したウォッチドッグが自動で復元します。手動復元はいつでも可能で、使うとその対戦の自動処理は停止します。

付加レイヤーの削除は、個別確認のうえで直接削除します。対象は AI コーチや iCreate 録画といった付加コンポーネントで、クライアントの更新時に再ダウンロードされます。ゲーム本体・ログイン経路・アップデーターは削除対象に含まれません。League、WeGame、アンチチートのいずれかが動作中は操作を拒否します。

一連の処理でプロセスへのインジェクション、メモリの改変、ゲーム中核ファイルやアンチチートへの干渉は行いません。ログイン資格情報はメモリ上で一時的に使うだけで、ログにもディスクにも書きません。この機能をオフにしている間はディスクのスキャンもクライアントへのアクセスも行いません。WeGame はログインユーザーの権限で起動するため、ゲームとアンチチートが巻き添えで昇格することもありません。

## HAGS と VBS

どちらもシステムの低レイヤー設定を変更するもので、再起動が必要です。元の値は先にスナップショットを取ります。VBS をオフにすると WSL2 / Docker / Hyper-V / Windows サンドボックスが使えなくなります。このトレードオフはご自身で判断してください。

これらは MPO やグラフィック / ネットワーク / USB の割り込みアフィニティと一緒に「システム環境」ページにあります。このページの項目はすべて再起動が必要で、しかも Pavise をアンインストールしても元には戻りません。ゲーム終了時に自動で戻るスケジューリング系の項目とは、そのため分けて配置しています。

## ビルド

Windows に同梱の .NET Framework C# コンパイラーだけでビルドできます。Visual Studio も、復元が必要なパッケージもありません。

```cmd
build.cmd
```

開発中は、古いインスタンスの終了・再ビルド・起動を 1 コマンドで行えます。

```cmd
dev.cmd        rem 古いインスタンスを終了 → Pavise.dev.exe をビルド → 起動
dev.cmd test   rem セルフテスト入りでビルドし、実行して結果を表示
```

スクリプトはまずアイコンを生成し、そのあと管理者マニフェスト・製品名・会社名・現在のファイルバージョンを含む `Pavise.exe` をビルドします。バージョン番号は `src/Program.cs` の `App.Version` が基準です。

ソースからのビルドには Authenticode 署名がありません。個人プロジェクトなら未署名のまま配布して構いません。発行者の身元確認や SmartScreen の挙動改善が必要な場合は、各自の信頼されたコード署名証明書をご利用ください。

## 実行とデータの保存先

- `Pavise.exe` をダブルクリックすると通知領域に常駐します
- 他のプロセスやシステム設定の変更には管理者権限が必要です
- 設定ページのメンテナンス欄にワンクリック復元があります
- スタートアップはタスクスケジューラで実現しています
- 起動後に GitHub のバージョンを 1 回確認するだけで、PC のデータは送信しません

既定のデータフォルダは `%AppData%\Pavise` です。

- `Pavise.profiles.dat` — 対象プロファイル
- `Pavise.whitelist.txt` — 許可リスト
- `Pavise.log` — 実行ログ
- レジストリ `HKCU\Software\Pavise` — 画面と機能のスイッチ

実行ファイルの隣に空の `Pavise.portable` を置き、そのフォルダが書き込み可能であれば、データはそちらに保存されます。

## ソース構成

- `src/Core` — 対象検出、スケジューリング、抑制、復元
- `src/Platform` — Windows API、設定、パス、サービスのラッパー
- `src/Ui` — WinForms 画面と自前描画コントロール。`src/Ui/Pages` は 1 ページ 1 ファイル、`src/Ui/Controls` にコントロール
- `tests` — 内蔵セルフテスト（`build.cmd xxx.exe --selftest` のときだけ組み込まれ、リリースビルドには含まれません）
- `scripts` — アプリのスモークテスト

`SetPriorityClass`、`SetProcessDefaultCpuSets`、`NtSetInformationProcess`、`SetProcessInformation`、`D3DKMTSetProcessSchedulingPriorityClass` などの Windows API を使用しています。プロセスの同一性判定には作成時刻も使うため、PID が再利用されても別のプロセスに変更が及ぶことはありません。

## 検証範囲

内蔵セルフテストは現在 `120` 件です。対象検出とセッション保護、抑制と復元（PID 再利用、クラッシュ後の復帰を含む）、CPU 構成と分割、プロファイル保存形式の互換性と未知バージョンの保護、ゲームスキャンとアクセラレーターの除外、学習機構の発動境界、システム診断の閾値、League 専用機能の境界、画面描画を扱います。環境に必要な機能がない場合は `PASS` ではなく `SKIP` と記録します。

同一コア競合テストは、2 つの計算プロセスを同じコアに置いて競合側を凍結するものです。CPU 時間を解放すればスループットが回復することを示すだけで、実ゲームの FPS や 1% Low の証拠ではありません。

### 抑制の効果を合成負荷で実測

`--contention-lab` は複数ラウンドの A/B ペア比較ベンチです。被害者側はシングルスレッドの定量フレームループ（スロットリングも垂直同期待ちもしないため、フレームタイムが取得できた CPU 時間をそのまま反映します）、競合側は論理プロセッサ数と同数の全負荷プロセスです。各ラウンドで「放置」と「隔離抑制」を交互に実行し、シミュレーションではなく実際の抑制処理を使います。

2026-08-02、6 コア 12 スレッドのノート PC での 6 ラウンドの結果：

| 指標 | 放置 | 隔離抑制 |
|---|---|---|
| フレームタイム中央値 | 0.65 ms | 0.65 ms |
| 下位 1% フレーム | 3.4 → 14.2 ms（ラウンドごとに悪化） | 1.09 ~ 1.30 ms（常に安定） |

6 ラウンドすべてで改善し、下位 1% フレームの改善中央値は **90.7%**、中央値フレームの改善は **0.0%** でした。「抑制はカクつきを減らすものであって平均 FPS を上げるものではない」という設計上の想定と一致し、この主張に本機のデータが付いたのは今回が初めてです。

特筆すべき点として、放置区間ではテール側のフレームが時間とともに悪化し続けた（3.4 ms から 14.2 ms へ）のに対し、抑制区間は同じ時間ずっと 1.1 ms 付近で安定していました。抑制はテールを下げるだけでなく、この時間経過による悪化そのものを防いでいます。

これは合成負荷です。被害者側は CPU のみで、GPU・VRAM・ディスク I/O はなく、スレッド構成も実ゲームよりはるかに単純です。「隔離抑制が CPU 競合によるフレームタイムのテール悪化を確かに遮断する」ことは示せますが、ここから実ゲームのフレームレート向上量を推定することはできません。

### 効果は優先度低下によるもので、コア分割によるものではない

同じベンチを 3 群比較（放置 / 優先度低下のみ / 優先度低下＋分割）に組み替えた 5 ラウンドの結果：

| 比較 | 下位 1% フレームの改善（各ラウンドの中央値） |
|---|---|
| 優先度低下のみ vs 放置 | 89.5% |
| 優先度低下＋分割 vs 放置 | 90.4% |
| 分割による追加寄与 | −2.0% |

**効果のほぼすべては優先度低下そのものによるもので、コア分割に測定可能な追加寄与はありませんでした。**

ただし同時に述べておくべき点があります。この 6 物理コアの環境では `HasSafeBackgroundPartition()` が false を返します。`CpuPartitionPolicy.BackgroundCoreCount` の既定方針では 6 コア以下にバックグラウンドコアを割り当てないため、`Isolated` 段階のコア固定処理はこの環境では実行されていません。したがって上表が示すのは「分割しない環境では優先度低下だけで効果を取り切っている」ということであって、「分割は無意味」ということではありません。分割自体の効果は 8 コア以上の環境で別途検証が必要です。

### 中央値フレームを改善できるのは凍結だけ

ベンチを 4 群（放置 / 優先度低下のみ / 優先度低下＋分割 / 凍結）に拡張したところ、独立した 2 回の実行が同じ結果を示しました。

| 段階 | 中央値フレーム | フレーム数 | 下位 1% フレーム |
|---|---|---|---|
| 放置 | 0.65 ms | 約 18000 | 1.5 ~ 18.3 ms |
| 優先度低下のみ | 0.65 ms | 約 22000 | 0.9 ~ 1.5 ms |
| 優先度低下＋分割 | 0.65 ms | 約 22000 | 0.9 ~ 1.4 ms |
| **凍結** | **0.59 ms** | **約 24800** | 0.8 ~ 1.0 ms |

前 3 段階の中央値はいずれも 0.65 ms で完全に一致し、凍結だけが 0.59 ms（−9.6%）まで下げました。しかも全ラウンドで例外なくそうなりました。理由は単純です。優先度低下と分割は順番を変えるだけで、抑制されたプロセスは CPU サイクルを消費し続けます。凍結は完全に止めるので、スループット自体が変わります（フレーム数 +11%）。

テール側での凍結の追加効果は安定しません（中央値でさらに 15% ~ 21% 改善しますが、ラウンド間のばらつきが大きい）。隔離段階の時点でテールがノイズ下限近くまで下がっており、改善の余地が残っていないためです。

各ラウンドの凍結は実効性を検証しています。段階を適用したあと抑制対象プロセスの CPU 時間を連続 2 回サンプリングし、すべて増加が止まっていた場合のみ統計に算入します。この検証がなければ「凍結したつもりで実は凍結できていない」データを結論としてしまう可能性がありました。

### 割り込みは CPU 0 にはない

ゲームの CPU アフィニティからスレッド 0 と 1 を外す、というやり方がよく知られています。「システムは最初のコアに固定される」という理屈です。`--irq-map` は `NtQuerySystemInformation` で各コアの DPC ＋割り込み時間の比率を測定します。開発機（Intel ハイブリッド、24 物理コア / 32 スレッド）で 30 秒窓・3 ラウンドの結果：

| 物理コア | 1 回目 | 2 回目 | 3 回目 |
|---|---|---|---|
| **4/5** | **1.77%** | **1.72%** | **2.40%** |
| 16 | 0.21% | 0.89% | 0.47% |
| **0/1（CPU 0 を含む）** | **0.00%** | **0.00%** | **0.05%** |

**割り込みは物理コア 4/5 に安定して集中しており、CPU 0 を含むコアはその 2% ~ 4% しかありません。** どのラウンドでも同じコアが選ばれ、対象は明確かつ安定しています。現在のデバイスは MSI-X で割り込みを分散させるため、どのコアが割り込みを担うかはその PC に何が入っているかで決まります。位置から決め打ちすると避けるコアを間違えます——この環境でスレッド 0/1 を外すのは、きれいなコアを手放したうえで、本当に汚れている 4/5 はゲーム側に残したままということです。

測定には注意すべき落とし穴があります。割り込み時間はクロック割り込み周期で積算されるため、3 秒窓では約 192 tick しかなく、**分解能は 0.52%** です。これを下回る負荷はすべて 0 に量子化されます。3 秒窓で最初に出た「ほとんどのコアが 0.0000%」は量子化ノイズであって、本当にきれいなわけではありません。正確な測定には 30 秒窓（分解能 0.05%）が必要です。

**このデータをもとに「実測でコアを選び、ゲームを割り込みコアから退避させる」機能を作りましたが（v1.6.2）、1 日で削除しました。** 理由は実装の不備ではありません——毎回正しいコアを選べていました。規模を評価し直した結果、結論が変わったからです。割り込み 1 回あたりの妨害はマイクロ秒級で、2% ~ 3% の占有は数万回の数十マイクロ秒のイベントに分散しており、1 回あたりでは 1 フレームの予算のうち体感できる割合を食いません。一方で物理コアを 1 つ手放すコストは確実です（ハイブリッド構成では P コアの 12.5%）。確実なコストを、測定ノイズに埋もれる可能性が高い利得と交換するのは成り立ちません。`DpcSampler` にもともとある 4% のストーム閾値のほうが正しい設計でした。本当の割り込みストーム（4K/8K マウス、異常なドライバー、10% 以上の水準）だけがコアを譲る価値があり、常態的にやや汚れている程度では割に合いません。

`--irq-map` 診断は残しています。この PC の割り込み分布が異常かどうか（5% を超えるならデバイスを調べるか、割り込みアフィニティで逃がすことを推奨）、そして「スレッド 0/1 を外す」という通説がこの PC では正しいコアを避けているのかどうかが分かります。システム診断ページにはその簡易版が内蔵されています。

NVIDIA 詳細設定の 3 項目（電源の最高パフォーマンス、フレームレート上限、事前レンダリング制限）は、開発機の RTX 3090 上で `--nv-probe` による書き込み・読み戻し・復元の実測を行い、**3 項目とも実際に反映される**ことを確認しました。削除済みの低遅延モードの設定 ID はドライバーに拒否され（NVAPI -160）、1.6.1 で削除した判断の裏付けになりました。診断ページに同じワンクリック実測があるので、各環境で確認できます。
