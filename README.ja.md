## 性能

上のグラフは v1.7.1 当時の 4 段階ベンチです。測定条件は、i7-9750H のノート PC で WeChat・Clash・QQ・音楽プレーヤーをバックグラウンドに常駐させ、クリーンな状態を 100 とした相対値です。3 シナリオの平均で、Pavise なしが 59、通常モード 60、競技モード 96 となりました。グラフの通常と競技が現在のスマートと集中で、極限モードは廃止されています。

Pavise は性能を新たに生み出すものではなく、バックグラウンドに取られていた分をゲームに戻すツールです。そのため、常駐プログラムが多く CPU やディスクの奪い合いが起きている環境ほど効果が大きく、もともとクリーンな環境や完全に GPU 律速のゲームでは変化は限定的です。

極限モードは高負荷シナリオで 71 にとどまり、競技モードの 93 を下回りました。これが廃止した理由です。抑制の強さと性能は比例しないため、既定のプリセットは最も穏やかな設定になっています。

実際の効果は、同じゲームの同じ場面でオン・オフを比較して確認してください。

## 実験機能：VidMm ビデオメモリ常駐

「最適化ポリシー」に実装済みの任意機能で、既定はオフです。実際のゲーム描画プロセスのビデオメモリ予算と使用量を調べ、予算への圧迫が継続し、アダプターが確認でき、既存の予約がない場合だけ控えめな予約を試み、結果を再読込して確認します。

VRAM を増量・固定する機能ではなく、ドライバーのインストールやゲームへの注入も行いません。アクセス拒否、内蔵 GPU のみの機体、アダプターが不明確な場合や書き込みを確認できない場合はスキップまたは停止します。ハイブリッド GPU の実際の描画経路は実機での検証が必要です。ゲーム終了時に本ツールの予約を解除し、復元未完了なら記録を保持します。

すべての環境でフレームレートが向上する保証はありません。効果とドライバー互換性は同条件の実機比較が必要で、API の成功だけではゲームが滑らかになったとは判断しません。

## 使い方

ゲームの EXE またはショートカットを対象ライブラリに追加します。スキャン機能で Steam / Epic / GOG / Ubisoft / Riot / WeGame / Battle.net / Xbox のインストール済みゲームを取り込むこともできます。

ゲームの実行中は自動で保護され、デスクトップへ切り替えても最小化しても解除されません。ランチャー経由で起動するゲーム（League of Legends など）は初回の確認後に本体を記憶し、次回から直接認識します。ランチャー・アップデーター・クラッシュレポーター・アンチチートのプロセスはゲームとして認識されません。

ゲーム終了時は記録に基づいて復元可能なセッション中の一時変更を戻します。Pavise が異常終了した場合は次回起動時に再試行し、失敗した復元の記録は保持します。アプリの GPU 設定は保存され、入力言語は戻さず、消去したキャッシュ内容も復元できません。

## モード

| モード | 抑制の範囲 |
|---|---|
| スマート | 対戦開始と同時に、保護境界を通過したバックグラウンドを一度にすべて隔離します。熱量は見ませんし、段階的に引き上げることもしません。使用中のプログラムとその一族には手を出しません |
| 集中 | 隔離の対象がゲーム以外の全体に広がります。ウィンドウを持つものも例外ではなく、ゲームから切り替えた先のプログラムも対象で、ホワイトリストのみ除外されます |
| カスタム | バックグラウンド抑制・コア・メモリと電源・システム環境・グラフィックスを項目ごとに選択 |

二つのモードの違いは抑制の強さではなく、どのプロセスが触れられる資格を持つかだけです。境界を通過したものは一律で即座に隔離し、十数秒リソースを食うのを待ってから動くことはしません。冷えたプロセスも対象です。隔離段階で書き込むのは最低優先度、最低のディスク IO とページ優先度、EcoQoS とタイマー精度の上限、そしてターボブーストの無効化で、GPU 譲渡をオンにしていれば GPU スケジューリング優先度も最低まで下げます。

これは 1.9 時代とは逆の方針ですが、前提が変わったためです。当時の全員隔離は確かに逆効果でした——百ものアイドルプロセスの散発的なタイマー起床が、アフィニティの絞り込みによって 2 コアへ押し込められ、互いに待ち行列を作って最長フレームが 2.6 倍になりました。2.0 からバックグラウンドのアフィニティは一切変更せず、絞り込みとコア移動は丸ごと廃止しています。実行可能スレッドを持たない冷えたプロセスはそもそも CPU を消費せず、たまに起きても、より高い優先度の仕事がないコアならどこでも走れます。待ち行列が消え、全員隔離の代償も一緒に消えました。

どのモードでも、アンチチート・対戦中のゲームホスト・Windows のコアサービス・ゲーム用アクセラレーター・他のログインユーザーは抑制されません。この境界はどのスイッチにも左右されません。自動除外の 4 分類（ゲームプラットフォームとランチャー、ネットワークアクセラレーター、アンチチート、入力・音声・周辺機器チェーン）はホワイトリストのページで直接確認できます。
## ゲームごとの個別設定

ライブラリでゲームを選び個別設定を開きます。各ゲームはモード・バックグラウンド抑制・コア・メモリと電源・システム環境・グラフィックスの設定を個別に上書きできます。上書きしていない項目はグローバル設定に従い、変更は即保存され、多くはそのゲームの次の対戦から反映されます。

- 多くのゲーム別設定は対戦開始時に決まり、変更は次の対戦から反映されます。非必須サービスの停止と CPU アイドルのスイッチは現在の対戦中にも処理し、オフにすると本機能の変更を戻します
- 現在のコア選択を特定のゲームに固定できます。他のゲームには影響しません
- 上書き一式はワンクリックでグローバルへ戻せます
- 概要ページとトレイには実際に有効なモードと、それがどのゲームの個別設定由来かを表示します
- ドライバー書き込みの連続失敗でスイッチが自動オフになるときは、そのゲームの該当する上書きも一緒に消去されます

ライブラリの項目は名前を変更できます。表示名だけが変わり、認識には影響しません。

## 機能

**プロセスとコア**

- ゲームプロセスに高優先度・より高いディスク IO と GPU スケジューリング優先度・専用コアを与え、バックグラウンドはモードに応じて降格します。バックグラウンドのアフィニティは変更せず、絞り込みも移動も行いません
- CPU パーティションはハイブリッド構成・X3D・複数プロセッサーグループに対応。6 コア以下では分割しません
- コア割り当ては論理コア単位で手動指定でき、全コア・ハイパースレッディング無効・P コアのみ・反転のプリセットがあります。変更は適用を押して確定します。多くの場合は触る必要がなく、スケジューラーが既定でゲームスレッドを P コアに置きます
- スマートフレーム保護：フレームレートを決めるスレッドを特定して単独で引き上げます。CPU 飽和時にベンチ実測で 1% Low が 77%〜96% 改善
- スマート譲渡：CPU の飽和が 10 秒続き、かつフレームスレッドが単独で引き継げなかった場合、ゲーム本体を一時的に通常優先度へ戻します。その状態ではプロセス全体の高優先度がテールフレームを悪化させることを実測しています。フレームスレッドの引き継ぎが成功するか CPU に余裕が戻れば、高優先度へ復帰します
- 対戦中の自己譲渡：Pavise 自身がゲームコアを明け渡し、自分のスケジューリング重みを下げます
- アンチチート互換リスト：書き込みを拒否されたゲームを記録し、失敗が確定している優先度と IO の書き込みは再試行しません。GPU スケジューリング優先度とフレームスレッドは通常どおり試みます。リストはバージョンが変われば自動失効し、アンチチートのページで確認と消去ができます

**グラフィックス**

- グラフィックスは「共通 / NVIDIA / AMD / Intel」のタブに分かれます。「共通 → アプリの GPU 設定」では EXE または実行中のバックグラウンドアプリを選び、Windows の省電力 GPU 設定を保存できます。内蔵 GPU と独立 GPU の両方を確認できる場合のみ追加し、Intel Arc B580 を内蔵 GPU と誤認しません。[アプリの次回起動時に反映](https://support.microsoft.com/en-US/Windows/Hardware/Display-Graphics/optimizations-for-windowed-games-in-windows-11)され、実行中のアプリを移動・再起動せず、ゲームによる独立 GPU の独占も保証しません。ゲームや Pavise の終了後も維持します。項目削除や全設定リセットでは本ソフトの変更だけを戻し、元からの省電力設定や検出した外部変更は残します。書き込みや復元を確認できない場合は復元記録を保持します
- Intel タブには「ゲーム中の Intel グローバル低遅延」を追加。既定はオフで、全体への影響を確認して有効化し、ゲーム別のオン・オフも指定できます。公式 IGCL がリアルタイム変更を明示した DX9/DX11 経路で基本 On のみ使い、Boost、XeSS フレーム生成、オーバークロック、FPS 上限は有効にしません。FPS 向上は保証しません。複数 GPU の場合も選択した Intel アダプターへの設定であり、ゲームが実際に使う GPU とは限りません。元から On/Boost なら変更せず、終了時は確認できた本ソフトの変更だけを戻します。未確認の書き込みから復元権を推測しません。対応状況はドライバーの能力報告に依存します。[Intel IGCL の定義](https://github.com/intel/drivers.gpu.control-library/blob/b6c462933502e13d1537dd5024949a51be30e63d/include/igcl_api.h)
- バックグラウンド GPU 譲渡：バックグラウンドが GPU を使っているとき、その GPU スケジューリング優先度も同時に下げます
- NVIDIA のゲームごと調整：電源管理を最大パフォーマンスに、低遅延モード（オンまたはウルトラ）、Smooth Motion によるフレーム生成、シェーダーキャッシュの上限解放、DLSS の上書き（最新または J・K 世代の指定）、ゲームごとの ReBAR。元の値はスナップショットに保存し、オフにすれば復元します
- GPU 電力上限：対戦中はベンダーが許す上限まで引き上げ、終了時にスナップショットから復元します

**キーボード・マウスと割り込み**

- ゲーム開始時の英語切り替え：「最適化ポリシー → セッション追加機能」に配置し、既定はオフ、ゲーム別に上書きできます。開始直後の短い待機期間内に、実際に前面にあるゲームへ利用可能な独立した英語キーボードレイアウトを一度だけ要求します。その後に中国語へ戻した場合やゲームへ戻った場合は介入せず、終了時も入力方式を戻しません。対戦途中の有効化は次回起動から反映し、Pavise 再起動時にすでに動いているゲームには要求しません。[Windows の入力言語要求](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchangerequest)を使い、キー入力の模擬、既定 IME やレイアウト共有方式の変更は行いません。IME の製品名に依存しませんが、英語レイアウト不足、権限制限、アプリ側の拒否時はスキップし、全 IME・ゲームへの対応は保証しません
- フィルターキー・固定キー・切り替えキーを無効化します。これらはマイクロソフトの定義そのものが短い打鍵を無視する機能で、有効なままでは必ず遅延が乗ります
- キーボードとマウスのセレクティブサスペンドを禁止します。少し放置した後の最初の操作がふらつく現象への対処です。触るのはキーボードとマウスだけで、USB メモリやサウンドカードには手を出しません
- 他のツールに変更された入力キューの長さを修復し、ポインターの精度を高める（システムのマウス加速カーブ）をオフにします
- フォアグラウンドのタイムスライスは 3 段階から選択：システム既定・フォアグラウンド優遇・報告のみ。フォアグラウンド優遇は旧来の最適化界で言う 0x26 で、機種依存でありベンチでも確実に勝てるわけではないため、選んだあとは同じ場面で自分で比較してください。それ以外の民間療法的な値はすべて異常として報告します
- GPU の割り込みアフィニティをレンダースレッドに近いコアへ寄せます。USB とストレージコントローラーの割り込みアフィニティは 1.8.1.0 で廃止しました。理由は後述します

**メモリと電源**

- 対戦時は既定で Pavise 管理の電源プランへ切り替えます。初回の対戦で自動作成し、各パラメーターはこのプロセッサーに合わせて書き込み、名前に PG タグとマシン署名が付きます。マシン上の任意のプランを選ぶこともでき、その場合 Pavise は切り替えるだけでパラメーターには一切触れません。設定は一度だけで定期的な巡回はしないため、他の電源ソフトとプランを取り合いません
- 管理プランは 2 系統に分かれます。集中モードは最小プロセッサー状態 100%・コアパーキングなし・エネルギー設定を最も性能寄り・Boost ポリシーを最大にします。スマートは降クロックの余地を残し、デスクトップではエネルギー設定を同じく最も性能寄りにして AC 接続時のクロックデューティ制御をオフにし、ノート PC には中間値を与えます
- CPU アイドルの無効化：「最適化ポリシー → セッション追加機能」に配置し、既定ではオフです。有効化のたびに警告を確認します。ゲーム中、AC 電源と確認でき、Pavise 管理の電源プランが有効な場合だけ適用し、AC 設定のみ変更します。無効化、ゲーム終了、バッテリーへの切り替え時に本機能の変更を戻し、ユーザーが選んだ別のプランは変更しません。消費電力、発熱、ファン騒音が増え、環境によってはクロックやフレームレートが下がる可能性があります。効果は自身で比較してください。性能の自動判定は行いません
- スタンバイメモリ整理（ISLC ルール）：「最適化ポリシー → セッション追加機能」に配置し、既定はオフ、有効化前に確認します。リスト量と実際の空きメモリの両条件を満たした場合だけスタンバイリスト全体を消去します。数値設定は全ゲーム共通で、スイッチのみゲーム別に変更できます。ゲームやバックグラウンドのワーキングセットは削減しません。詳細は後述します
- 電力譲渡：ノート PC では CPU と GPU が同じ電力と排熱の予算を分け合うため、GPU が上限に張り付き CPU に余裕があるとき、エネルギー効率設定を性能寄りのまま中間値へ動かし、予算を GPU へ流します。既定はオフで、ノート PC・電源接続・集中段階・Pavise 管理の電源プラン・RAPL のワット数が読めること、すべて満たす場合のみ参加し、1 対戦につき 1 回だけ判断します。20 秒観察して決定し、実行後さらに 15 秒検証、3W 以上譲れないか GPU 利用率が 3% 以上落ちれば即座に差し戻し、自動試行を停止します。条件を満たす場合にユーザーが確認して再度オンにしたときだけ再試行します。作者の i7-9750H では EPP を全域で振ってもパッケージ電力も実周波数も動かず、この種の機体では必ず検証に落ちます。それが意図した動作です
- MMCSS マルチメディアスケジューリング：非マルチメディア処理向けの予約を 20% から 10% に下げ、Games タスクのスケジューリングカテゴリーとファイル IO を高に上げます。ゲームモードが有効な間は維持され、オフにするか終了すると復元します
- Game DVR のバックグラウンド録画はゲームモードが有効な間オフのままにし、Pavise の終了時に復元します。システムがゲーム起動の瞬間に読み取る設定のため、ゲームより先に整っていなければ効きません
- 電源プラン・ネットワーク・通知はゲーム終了後にすべて復元します

**システム環境**

再起動が必要なもの、あるいはマシンに残る変更はこのページにまとめています。すべて復元可能です：

- ハードウェア アクセラレータによる GPU スケジューリング（HAGS）。平均フレームレートへの影響は誤差の範囲で、意味があるのはドライバ側のフレーム生成などの前提条件である点です。オフのままではそれらが使えません。非対応の環境ではグレーアウトします
- VBS 仮想化ベースのセキュリティの無効化。有効化前にリスク確認があります
- CPU の投機的実行脆弱性に対するソフトウェア緩和の解除。カーネル遷移ごとの固定コストを回収します。回収できるコストが実際に計測された環境でのみ解放されます
- ゲームモード保護、ウィンドウ表示ゲームの最適化、デバイスの電源

**目に見える部分**

- システム診断ページ：このマシンの能力を読み取り専用で点検し、各結論に根拠のレベルを表示します。サードパーティ製ツールに壊された項目はその場でワンクリック修復でき、GPU が現在電力上限か温度上限に当たっているかも確認できます。割り込みの行はカーネル ETW で DPC と ISR を捕捉し、最大の発生源を名指しします
- セッションレポート：プレイ時間、抑制したプロセス数とその CPU 占有、電力上限と温度上限に当たっていた時間の割合、そしてゲームがシステムメモリへ溢れさせた共有ビデオメモリのピーク
- ライブラリは強制引き継ぎに対応します。エミュレーターやクラウドゲーミングのように認識できないものは、プロセスが起動した時点で対戦として扱います
- ホワイトリストは独立したページで、ドラッグして入れるだけで適用範囲は自動判定します

完全にローカルなツールです。サービスをインストールせず、データを送信せず、ゲームプロセスへ注入せず、ゲームのメモリやファイルを書き換えません。各書き込みは可能な限り読み戻して照合し、期待値が読めなければ成功とみなしません。

## メモリ整理

**任意機能：スタンバイメモリ整理（ISLC ルール）。既定はオフです。** 「最適化ポリシー → セッション追加機能」で有効にし、隣の設定ボタンでリスト量の閾値、空きメモリの閾値、確認間隔をまとめて保存します。Pavise の既定値は 1024 MB、1024 MB、4000 ms です。MB は 1024² バイトで、閾値は 0～1048576 MB、間隔は 250～300000 ms の範囲です。各版 ISLC の初期設定と同一であるという意味ではありません。

条件は `List ≥ リスト閾値 AND Free < 空き閾値` です。List はスタンバイとシステムワーキングセットの合計、Free は Free + Zero ページのみです。タスクマネージャーの Available にはスタンバイが含まれ、Free の代用にはなりません。[ISLC 作者の説明](https://www.wagnardsoft.com/forums/viewtopic.php?p=6381)、[Microsoft の計数定義](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)。

ゲームセッションを検出している間だけ、独立したワーカーが `MemoryPurgeStandbyList` で全優先度のスタンバイページを消去します。プロセスやシステムのワーキングセット、変更済みページ、メモリ結合、圧縮、ページファイル、タイマー精度は変更しません。並列実行や遅れた確認の連続実行はせず、隠れた追加クールダウンもありません。読み取りまたは消去が連続 2 回失敗すると無効化し、再度有効にするには確認が必要です。

現在のゲームに適用される設定の無効化やゲーム終了、Pavise 終了で未実行の処理を取り消します。すでに Windows に入った呼び出しは中断できず、終了時は完了を待ちます。破棄したキャッシュは元に戻せません。全体設定は既定値であり、ゲーム別のオンが全体のオフより優先されます。止めるにはそのゲームの個別設定をオフにするか、ゲーム保護全体をオフにしてください。ディスク読み取りやロード時間、一時的なカクつきが増える可能性があり、全環境での性能向上や無事故は保証しません。他の自動整理ツールとの併用は避けてください。数値設定は全ゲーム共通です。実装対象は ISLC の主要なメモリルールであり、独立した起動管理、除外リスト画面、任意のタイマー設定は含みません。

**以下は旧実装の測定記録であり、新しいポリシーの性能試験結果ではありません。**

下表は、この種のツールが使うシステムレベルのコマンドを個別に測定したものです。測定機はメモリ 64 GB、測定前の空きは 40344 MB、システムキャッシュは 16154 MB：

| コマンド | 所要時間 | 空きメモリ | システムキャッシュ |
|---|---|---|---|
| 全プロセスのワーキングセットを空にする | 1894.9 ms | +5191 MB | +3364 MB |
| スタンバイリストの消去（低優先度） | 13.3 ms | +144 MB | −47 MB |
| スタンバイリストの消去（全体） | 1380.6 ms | +382 MB | −18894 MB |
| 変更済みページリストのフラッシュ | 8019.7 ms | +5845 MB | +251 MB |
| 物理メモリページの結合 | 6152.1 ms | +2121 MB | +531 MB |

スタンバイリスト全体の消去は、18894 MB のシステムキャッシュを捨てて 382 MB の空きメモリしか得られません。スタンバイリストはもともと空きメモリに数えられているため、消去とは「キャッシュされた空きメモリ」を「空っぽの空きメモリ」に変える操作で、総量はほとんど動かず、キャッシュ内容は失われ、直後のゲームロードはディスクから読み直しになります。変更済みページリストのフラッシュは 8 秒、ページ結合は 6.2 秒かかり、どちらも対戦開始の経路に置ける処理ではありません。

**削除：メモリ逼迫時に低優先度スタンバイメモリを整理**

この項目は「教訓を踏まえて残した版」と見なされていましたが、2026-08-20 の実測により、より見えにくい形で同じ罠を踏んでいたことが判明しました。

トリガー条件は空きメモリの比率ですが、空きメモリはそもそもスタンバイページを含みます。整理はページをスタンバイリストから空きリストへ移すだけなので比率は変わらず、条件は永久に解除されません。45 秒のクールダウンは、無限の繰り返しに拍子を与えていただけでした。実際のユーザーログでは 10 分間に 14 回、正確に 45 秒間隔で発火し、止まることがありませんでした。

さらに重要なのは、ほとんど何もしていなかったことです。`MemoryPurgeLowPriorityStandbyList` が消すのは優先度 0 の階層だけで、24GB の機体ではその階層は合計 1.4 MB、1 回の実際の解放量は 0.0〜0.1 MB、呼び出しコストは 0.2 ミリ秒でした。節約できるのはメモリマネージャーのページ回収数百ナノ秒分で、1 フレームの予算に対してはノイズです。

**削除：対戦が安定した後にバックグラウンドのワーキングセットを回収**

`SetProcessWorkingSetSize` をプロセスごとに呼んでもメモリは解放されません。ページをワーキングセットからスタンバイリストへ追い出すだけで、そのうちダーティなページはページファイルへの書き込みが先に必要になり、そのディスク IO がちょうど対戦中に落ちます。しかも対象はすでに抑制済みのバックグラウンドプロセスで、メモリマネージャーが圧力下で最初に削る相手そのものです。サスペンドされていないため削った直後にページフォールトで読み戻し、数秒後にはこの作業が無駄になり、実質的に対戦中の読み書きが 1 往復増えるだけです。

**削除：Available を使った旧スタンバイリスト全消去**

旧実装は `スタンバイ 1 GB 以上かつ Available 1 GB 以下` を 5 秒ごとに確認していました。ISLC の Free とは異なる指標であり、その発火条件を再現していたわけではありません。上の過去の測定では全消去の呼び出しが約 1380 ms、システムキャッシュの減少が約 18894 MB、Available の増加が約 382 MB でした。旧版と低優先度版は引き続き削除済みです。新しいポリシーは本来の Free を使用しますが、キャッシュ破棄に伴う追加読み取りの負担は残り、呼び出し成功だけではゲームの滑らかさを証明できません。

関連する論考は Mark Russinovich『The Memory-Optimization Hoax』（Windows and .NET Magazine、2004 年 1 月）を参照してください。

## やらないこと

流布しているキーボード・マウス系のレジストリ最適化は、その多くが 0.1 ミリ秒台に作用するもので、遅延の主な発生源はレンダーキューです。この種の項目について Pavise は報告のみで変更しません。Bluetooth マウスや 125 Hz のポーリングレートも同様で、診断ページが名指しはしますが、変更するかどうかは利用者の判断です。

MSI モード、低遅延モード、バックグラウンドのフレーム上限、ゲームファイルのプリロード、位置による CPU 0/1 の除外はいずれも実装後に削除しました。理由はそれぞれ、実測で無効だった、デバイスを壊すリスクがあった、意味の取り違えだった——ドライバーのバックグラウンドフレーム上限は実際にはフォーカスを失ったアプリに作用するため、ゲームから切り替えると制限されるのはゲーム自身でした。

ドライバーレベルのフレームレート上限（NVIDIA と AMD）は 1.8.0.3 で廃止しました。上限はゲーム内設定かグラフィックスコントロールパネルで指定するほうが直接的で、ドライバー層で二重に掛けるとゲーム自身のリミッターや VRR と競合しやすいためです。AMD 側は Radeon Chill を経由する必要があり、これは Anti-Lag と排他なので、遅延最適化を別の遅延最適化と引き換えにすることになります。

1.8.1.0 ではさらに 3 項目を戻しました。USB とストレージコントローラーの割り込みアフィニティは、P コアが少ないハイブリッド構成で割り込みを低クロックの E コアへ落とし、高ポーリングレートのマウスで放置後の最初のクリックがふらつく原因になりました。単独の対戦時コアパーキング解除の上書きは、管理電源プラン側のパーキング設定と重複していました。ゲームごとの高性能 GPU 強制指定は、現代の Windows がもともとゲームに dGPU を選ぶためです。レンダースレッドに近いコアを狙う GPU 割り込みアフィニティは維持しています。

競技モードによるプロセッサーアイドルの自動無効化も同じバージョンで廃止しました。現在は既定オフの手動ポリシーで、有効化前にリスクの確認が必要です。プリセットによる自動有効化と旧版の周波数負荷テストは行いません。

極限モードと League of Legends 特集は 1.8.0.2 で廃止し、集中が最上位になりました。

フォールバック昇格（IFEO）とゲームごとの CFG 無効化は削除しました。全体・ゲーム別の操作項目、起動時の事前設定、セッション中の書き込みを廃止し、旧項目の互換処理は追加しません。削除済みのゲーム別項目を含むライブラリは既存のエラー処理に従い、システム変更の復元、旧データの自動消去、ダイアログ表示後に終了します。消去に失敗した場合は復元記録を保持し、理由を表示します。

過去の変更を復元する処理は残しています。通常の起動や更新では自動復元せず、設定ページのクリアボタンで戻します。ライブラリの非互換や読み書きの失敗時は、上記の自動消去と終了の処理を行います。

## 実行とデータの保存場所

`Pavise.exe` をダブルクリックするとトレイに入ります。電子署名がないため SmartScreen の警告が出ることがありますが、そのまま実行を選べば問題ありません。他プロセスを調整するには管理者権限が必要です。自動起動はタスクスケジューラで実装しています。起動時に公式の更新元へバージョンを 1 回だけ確認し、ローカルのデータは送信しません。

データは既定で `%AppData%\Pavise` に保存されます（対象設定・ホワイトリスト・動作ログ）。画面と機能のスイッチはレジストリの `HKCU\Software\Pavise` に保存されます。実行ファイルの隣に空のファイル `Pavise.portable` を置くと、プログラムのディレクトリに保存するようになります。

設定ページにワンクリックの復元があります。
