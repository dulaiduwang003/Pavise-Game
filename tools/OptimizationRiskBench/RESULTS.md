## 1. 自有工作集修剪

分配并触碰 256 MiB 私有内存；每次观测前重新触碰以恢复驻留，按 A-B-B-A 重复三组。A 不修剪，B 只对测试进程调用 EmptyWorkingSet。没有制造内存压力或清空系统缓存。

| 指标 | 不修剪（6 次） | 修剪（6 次） |
|---|---:|---:|
| 重新逐页访问耗时中位数 | 0.9189 ms | 50.7389 ms |
| 最小～最大耗时 | 0.8867～1.2814 ms | 50.2266～51.4628 ms |
| 访问期间新增总缺页 | 0 | 65,551～65,552 |

这证明修剪后存在真实回访成本，不证明产生同等游戏帧时间损失。计数包含软/硬缺页，未分类，不能写成“读盘 6.55 万次”。修剪动作本身的时间不包含在 retouch 指标中。

当前机器可用内存没有触发生产修剪阈值。另用纯函数验证，64 GiB 总量、12 GiB 可用时生产 ShouldTrim 返回 true；这是合成边界用例，不是本机当前内存状态。

## 2. CPU 耗时识别与错误提权

构造两个自有线程：固定计算后 Sleep(1) 的“帧样循环”，以及与它没有依赖关系的持续计算线程。调用生产 RenderLane.TryIdentify 三次，再交给生产 LaneJudge。只对被选中的自有工作线程改变线程优先级，并回读；不调用生产提权生命周期、不改变进程优先级、不动其他进程。

首轮同逻辑核争用，A-B-B-A 重复两组（每臂四秒）：

- 八个独立进程中，全部把无关持续计算线程选为提权对象，最小候选 CPU 份额约 91.5%～91.9%。
- 不提权：每个窗口得到 125～128 个完整循环间隔样本，p50 约 31.69～31.85 ms。
- 提到 THREAD_PRIORITY_HIGHEST：四个窗口均没有完整循环间隔样本，因此 p50/p99 为 NaN，不能编造百分位或写成“游戏 FPS 归零”。

追加分核对照：两个线程分别放在逻辑 CPU 2 和 4，A-B-B-A 一组。四次依然误认无关计算线程，但没有复现上述停顿：

| 每臂统计量的中位数 | 不提权 | 提权 |
|---|---:|---:|
| p50 循环间隔 | 15.4653 ms | 15.3968 ms |
| p95 循环间隔 | 16.0345 ms | 16.0271 ms |

分核差异很小，不能称为收益。Sleep(1) 受计时器粒度影响；这些绝对耗时不是游戏帧时间。首轮记录完整间隔样本；分核版本额外限制窗口结束边界，并独立记录窗口内完成次数，两版源码均随原始结果归档。

这是刻意构造的争用反例，不代表 Pavise 默认把游戏塞进单核。它证实了“CPU 最忙即帧关键”的误判，以及错误提权在争用下伤害另一条关键线程的可能；不能外推所有游戏的发生率或掉帧幅度。

## 第二轮：真实音频、缓存并发、现有台架（2026-09-05 18:56～19:04）

本轮不改正式调优代码。用户在另一台电脑操作。当前未发现 Pavise.dev 运行，基线中的该进程指标为 NaN（不可用），不是 0；不可与第一轮的软件占用或 GPU 温度直接拼接比较。

### 音频：机制生效，不能直接删作“负优化”

直接调用当前生产 AudioLowLatency.Activate/Restore，并用 IAudioClient3.GetCurrentSharedModeEnginePeriod 回读。A-B-B-A 四臂，所有 HRESULT 为 0：

- 采样率 44,100 Hz，默认 448 帧（10.1587 ms），设备最小 128 帧（2.9025 ms）。
- 两次开启均为 448 → 128 → 448 帧，生产 active=true，释放流后回到原周期。
- 两次基线保持 448 帧。没有播放、录制声音，也没有切换默认音频设备。
- 这里只验证共享音频引擎周期；不是端到端音频延迟、FPS、爆音率或低配机器压力下的表现。短时整机 CPU 样本波动重叠，不能据此宣称零开销或精确额外开销。

微软将该接口的结果定义为即时引擎周期，其他客户端可能改变它：[GetCurrentSharedModeEnginePeriod](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getcurrentsharedmodeengineperiod)。

### 缓存：未复现一致的并发负优化

沿用 GainBench2133 的对齐、无缓冲写文件方法，改用当前生产 CacheWarm.Run、8 MiB 分块和 50 ms 间隔。NVMe 采用显式手动路径；极限强制路径本来会跳过。每臂新建相互独立的 64 MiB 前景读取文件和 512 MiB 预热文件，前景做两秒 4KiB 对齐随机无缓冲读取。无缓冲只绕过 Windows 文件缓存，不保证设备内部缓存冷。

|---|---:|---:|---:|
| 关闭 A1 | 18,470.31 | 68.9 μs | 83.5 μs |
| 开启 B1 | 17,779.94 | 70.7 μs | 81.3 μs |

### 回归通过不等于所有台架通过

- 当前源码隔离自检：66/66 套件通过。
- 项目 RendererHandoffBench 原样运行 Repeat=3 两次：第一轮 138 条记录中 2 条失败；复跑 138 条记录中 1 条失败。三条失败不能被聚合 PASS 掩盖。
- 首轮失败：repeat=2 same-root/Standard-family-False-anchor-launcher（交接 epoch 变化）；repeat=2 split-root/trusted-root-after-launcher-exit（无法设置档案家族策略）。复跑失败：repeat=2 same-root/trusted-root-after-launcher-exit（交接 epoch 变化）。
- 对应日志出现档案替换 IOException，包括“无法删除要被替换的文件”。不能把 focused 套件故意注入的保存失败日志也计成真实额外失败；以上计数只取 FAIL 记录。
- 生产 GameProfileStore.CommitStrict 直接 File.Replace；Save 捕获异常后设置 saveFailed。GameMode.SignalProfileStoreSaveFailure 随后使交接 epoch 失效。这是保存失败保护路径，不是发现了 GPU/CPU 性能损失。原始占用者尚未确认，不归因于杀软。

新增最小存档实验仅持有自建档案的只读、不共享删除句柄。生产 Save 在持锁时失败，原文件完整；释放锁后同一实例仍拒绝保存，新建实例则保存成功。确认故障状态会持续到实例结束。改进方向是有限、可区分错误的重试及安全恢复，不应撤掉原子保存或简单吞错。当前未实施修复。
