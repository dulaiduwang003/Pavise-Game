# DX12 双 GPU 测试协议

## 实验范围与历史结果

问题是：在相同场景生成和相同后处理工作量下，把后处理从独显交给核显，是否能在包含已实现的跨适配器开销后稳定提高计算吞吐，并且不损害尾部完成间隔？

当前台架仅运行自有的 DX12 离屏计算，不捕获游戏、不创建交换链、不调用 `Present`。`single` 的结果位于主 GPU，`heterogeneous` 的结果位于辅助 GPU。指标是 **compute-stage 吞吐**，不是游戏显示 FPS，也不包含把辅助 GPU 输出送回实际接屏显卡的完整成本。

`RESULT-20260817.md` 是旧环境 RTX 3090 + UHD 770 的历史记录，不是当前这次机器/驱动/程序版本的测量。用户补充旧测试期间有其他电脑操作，故该结果仅用于回溯，待受控复验；既不能据此否定整个方向，也不能把旧报告数值当作新结果。

## 构建与运行边界

- 构建脚本只编译，不下载工具、不安装组件、不运行 GPU。
- 保存 `build-manifest.json`：必须为 `status: success`，并核对实际运行 EXE 的 SHA-256。该文件记录编译器路径/版本、源码与二进制哈希、UTC 构建时间。
- 无参数仅显示计划；`--self-test` 验证统计逻辑，不创建 D3D 设备。
- `--list-adapters` 用于确认适配器身份，不进行性能计分。
- `--validate-only` 会执行有限的 GPU 像素正确性检查，不是纯 CPU 自测，也不是性能结果。包装器的 `-ValidateOnly` 不要求 CPU 低占用，但仍检查键鼠、AC、NVIDIA 温度及超时。
- 只有明确的 `--run` 才进入性能测量。能力探针只验证资源/共享句柄，不计分。
- 不注入游戏、不访问游戏内部命令列表、不安装驱动、不修改系统电源/显卡设置。不要为了安静测试自动终止用户进程或关闭安全服务。

## 测试前固定条件

1. 记录系统版本、两张显卡名称、厂商/设备 ID、硬件 LUID、驱动版本、显示连接拓扑，以及本轮全部命令行参数。适配器编号可能变动，不能猜测 `0/1`。用 `--list-adapters` 核对名称/LUID后指定；2026-08-27 本机实测使用主 GPU `1`（RTX 2070 Max-Q）到辅助 GPU `0`（UHD 630），不是把主 GPU 默认当作 index 0。
2. 固定分辨率、像素格式、scene/post loops、帧数、帧槽数、主 GPU 传输路径、辅助 GPU 输入方式、输入序列、驱动配置及电源方案。筛查参数与独立确认参数分别保存，不混合统计。
3. **用户不动鼠标不等于机器空闲。** 远控服务、桌面合成、开发工具界面、视频/浏览器动画等仍可占用核显。记录后台 CPU/GPU 活动与观察到的干扰，监测方式、采样频率及开销在 A/B 中保持一致。不静默停止远控/服务器进程，不读取或转储环境密钥。
4. 测试前设置固定的热稳定过程。`--precondition-seconds` 默认为 `0`，这不表示已经完成热稳定；正式测试须显式记录选定的时长及理由。每阶段仍执行相同数量的预热帧，预热不写入正式逐帧样本。
5. 出现操作、后台突发、温度/时钟漂移或设备异常时，把整个受影响的配对块标记为受扰，保存原始数据并重跑完整块。不得只删除不利于异构模式的帧或阶段。

默认每阶段 120 帧预热、600 帧测量适合短筛查；在高帧率下可能只有数秒，不能单凭一次筛查确认百分之几的稳定提升。正式确认需增加持续时间和独立重复次数，使收益能与基线噪声区分。

`Run-ControlledBench.ps1` 提供基础实验守护：成功 manifest 与源码/EXE 哈希检查、唯一结果目录、CPU/输入/AC 与 NVIDIA 遥测采样。GPU engine 枚举只在计时前后进行。包装器要求有效 NVIDIA 温度；遥测缺失、非数值/NaN、查询失败或超时均拒绝启动或停止自有台架。输入恢复、失 AC、NVIDIA 达到设定温度（默认 83°C）或整轮超时同样只停止自有台架，不停止远控/服务器等其他进程。

该温度守护仅覆盖 NVIDIA，不覆盖 CPU/核显；不能把 NVIDIA 未超阈值解释为整机热安全。`environment_valid` 只表明本次可观察的输入、供电、NVIDIA 温度、超时、构建来源和结果契约守护通过，不证明机器无噪声。后台 GPU 活动仍未受控制。

## 环境分层与测前修订

每轮都保存 `environment_regime`，不同环境的数据不得混在一起宣称同一种收益：

- `correctness_only_not_timed`：只验证图像链路，不计性能，不要求 CPU 低占用。
- `idle_gated`：性能启动预检要求连续三个 CPU 样本不超过 20%，同时满足键鼠、AC 和温度等门槛；仍需分析后台 GPU 活动与时钟/基线噪声。
- `background_loaded_screening`：只有显式传入 `-AllowBackgroundLoadScreening` 才启用。连续三个 CPU 样本上限为 50%，其他正确性、计时、漂移、收益、键鼠、AC、温度及超时门槛全部不变。只允许描述为带已记录后台负载的探索结果，不允许宣称闲置电脑收益。

后台筛查不是静默失败回退。必须在计时测试前记录原因、环境与解释限制；不能看过收益后才变更环境标签或放宽门槛。任何正候选都必须在安静环境使用同一冻结参数独立确认，才能进入后续端到端验证。

2026-08-27 的修订已写入 [EXPERIMENT-20260827.json](EXPERIMENT-20260827.json)：首次严格空闲预检的 55 个 CPU 样本为 22.42–41.26%，均值 29.528%，因此没有启动 GPU 性能测试。最小化 GameViewer 主界面后远控连接仍在、CPU 仍约 30%；没有停止任何用户/远控进程。随后在性能测量前明确选择带后台负载的四用例筛查，不能将这一步表述为“机器已完全闲置”。

该机 `1 → 0` 的资源探针，以及 1080p `scene100/post4` 的 `direct/copy` 三 seed 预检已通过：源图、最终输出全图及 CPU 参考抽样均无误差。这只证明当前两条资源处理路径正确，不提供吞吐或游戏 FPS 收益结论。

## 传输路径与像素正确性

主 GPU 传输路径必须单独报告，不能合并挑选后的最优阶段：

- `--transfer-path direct`：主 GPU 场景直接写跨适配器共享缓冲区。
- `--transfer-path copy`：主 GPU 场景先写本地缓冲区，再经 `CopyBufferRegion` 写入共享缓冲区；复制与屏障计入 `scene_gpu_ms`。

辅助 GPU 输入方式是独立选项，默认 `shared`：

- `--secondary-input shared`：后处理直接读取共享缓冲区。
- `--secondary-input local`：辅助 GPU 先把共享输入经 `CopyBufferRegion` 复制到自己创建的普通 `DEFAULT` 缓冲区，再执行不变的后处理。辅助端起始 timestamp 位于复制前，复制、资源屏障和后处理全部计入 `post_gpu_ms`，也计入最终完成/wall 吞吐。

两种输入方式的输出都留在辅助 GPU，不包含显示回传。不能把 local 复制放在计时区外，不能只统计局部缓存之后的 shader 加速而忽略总成本。UMA 核显上的普通 `DEFAULT` 缓冲区不等于独立显存；假设涉及共享读取/缓存一致性的可能代价，不是已证明的瓶颈归因，也不保证复制更快。

开始计分前，固定 seed `0 / 41 / 193`，检查单卡与双卡输出并生成 `validation.json`：

- 主 GPU 场景源图逐像素相同，最终 RGB 各通道误差不超过 1，alpha 必须为 255。
- 每个输入对 CPU 后处理参考执行最多约 4160 个抽样核对，同时保存全图比较结果。CPU 抽样不能替代全图 A/B 比较。
- 检查跨 seed 输出确实更新，排除旧帧、全零数据、错位复制或错误 stride。
- 每种待测传输/输入组合都验证，不能用 `direct` 的校验代替 `copy`，也不能用旧 `shared` 校验代替新 `local`。局部输入路径必须读回辅助 GPU 实际使用的 `DEFAULT` 输入，检查复制后内容。容差在测量前固定，不能看到失败再放宽。
- 正确性读回在性能计时区外完成，额外开销不能只加在单卡基线中。
- 任何像素校验失败都禁止候选收益结论；正确性文件必须与同次参数和二进制对应。

## 辅助 GPU 局部输入的固定后续对照

原四用例已全部得到 `NO_BENEFIT`；原 C++、runner、EXE 和构建清单保存在 `results/build-original-7443C580`。不改写旧结果，也不把局部输入的新构建冒充原始复验。

后续假设与矩阵在 [EXPERIMENT-20260827-LOCAL-INPUT.json](EXPERIMENT-20260827-LOCAL-INPUT.json) 中预登记，不在看到结果后搜索更多中间参数：

- 新二进制先通过 CPU 自测及 `direct/local`、`copy/local` 像素预检；原算法、容差、单卡基线、三帧槽同步所有权和收益门槛不变。
- 固定 `direct / post4 / 1080p`，在 `scene100` 和 `scene600` 下分别运行 `shared` 与 `local`，每次仍执行完整 ABBA/BAAB/ABBA。
- 预热 120 帧、测量 600 帧、预运行 15 秒；环境仍为 `background_loaded_screening`，保留全部安全守护，不关闭远控或用户应用。
- shared 对照也使用新二进制重新运行，避免把不同构建/时段/背景负载的差异误认为局部输入收益。
- 每个候选必须战胜自己的单卡基线并满足全部原门槛，不能只战胜旧双卡实现。正候选仍需安静环境独立确认及最终显示链路验证。
- 如果固定矩阵没有任何候选通过，停止这一工作负载/参数方向的探索并如实报告，不增加误导性的正式加速开关。

## 顺序、指标与统计

每个阶段预热后再测量，默认交替三块：

1. `single, heterogeneous, heterogeneous, single`（ABBA）；
2. `heterogeneous, single, single, heterogeneous`（BAAB）；
3. `single, heterogeneous, heterogeneous, single`（ABBA）。

每块按相邻阶段组成两个不重叠的 A/B 配对，方向统一为异构相对单卡变化。报告全部阶段和配对，而不是把所有帧混成没有顺序信息的总体平均数。偶数个阶段的中位数取中间两个值的平均值。

主要指标：

- 计算平均 FPS：`1000 / mean(完成间隔 ms)`；它不是 `mean(逐帧 FPS)`。
- 1% low：最慢 1% 完成间隔的平均值换算成 FPS，样本数少的短跑只作筛查。
- 完成间隔 P50/P95/P99。
- 包含流水线填充/排空和 CPU 提交开销的阶段 wall FPS。
- 主 GPU 场景/后处理时间、辅助 GPU 后处理时间，以及已包含的传输成本。
- 配对胜负、各模式阶段分布、基线漂移与独立重复之间的变化。

首帧没有前一完成时间，不参与稳态完成间隔统计。每张 GPU 的 timestamp 使用该队列查询的频率换算；不同 GPU 的原始计数不能直接相减。结束间隔必须来自同一时钟域。设备丢失或时间戳无效不得被转成零耗时。

GPU 稳态吞吐与 wall 吞吐可能因流水线填充/排空、CPU 提交等产生差异，但必须一起用于判定。本协议要求每阶段二者相对差异不超过 5%；短跑未满足时扩大采样并检查计时，不能只引用较好的一项。

## DX12 有效性门槛

- 两个适配器具有不同硬件 LUID，且均成功创建 D3D12 硬件设备；排除 WARP/软件适配器。
- 跨适配器共享 heap/buffer 和 `D3D12_FENCE_FLAG_SHARED_CROSS_ADAPTER` fence 创建、打开及同步成功。DX12 路径不以 D3D11 keyed mutex 或 disjoint 查询作为有效性依据。
- 所有阶段完成预定帧数，时间戳频率有效，完成顺序和间隔有效，无设备移除、超时、共享失败或像素校验失败。
- 每阶段 wall 与 GPU 完成吞吐差异超过 5% 时判无效。
- 单卡全部阶段的计算平均 FPS、wall FPS 任一 `max/min - 1` 超过 5% 时判无效。检查整个基线分布，不用首尾偶然接近掩盖中途噪声。
- 后台噪声、热稳定、独立重复及原始结果完整性还需要协议层检查。程序输出一个候选标记，不代表外部环境已经自动通过。

## 候选收益门槛

只有在有效性门槛通过后，同时满足以下条件，才能称为“本负载的计算阶段候选收益”：

- 异构模式中位计算平均 FPS 和中位 wall FPS 相对单卡均至少 `+2%`；
- 异构模式中位 1% low 相对单卡至少 `+1%`；
- 至少 2/3 的局部不重叠 A/B 配对中，异构模式的计算平均 FPS 和 wall FPS 均不下降；
- 异构模式阶段 P99 的中位数不得恶化超过 5%；
- 正式确认沿用冻结的参数，独立重复后仍能成立，收益不能被已观察到的基线噪声解释。

`background_loaded_screening` 中的 `CANDIDATE` 仅有资格进入安静环境的独立确认，不满足该确认前不得升级为闲置性能结论或实装资格。

自动判定分为 `INVALID`、`NO_BENEFIT`、`CANDIDATE`，区分证据无效与没有达到收益门槛。`--run` 无效退出码为 2；有效但无收益与候选收益均为 0，故**退出 0 不能解释为提速成功**。`--validate-only` 成功的 `verdict` 为 null，只表示正确性校验通过。

占用率上升、核显开始工作、单个阶段领先，均不等于性能提升。

## 归档与实装门槛

保留本轮 `frames.csv`、`phases.csv`、`summary.json`、`validation.json`、`report.txt` 及 `build-manifest.json`。`summary.json` 使用 schema 2，范围为 `owned_offscreen_compute_only`，`product_ready` 固定为 false。同时归档完整参数、环境记录、测试时间、退出码和文件哈希；临时目录不是长期证据仓库。

`secondary_input` 扩展保持 schema 2，写入 summary 顶层/config 和 validation，并作为 CSV 末列追加。保留原列顺序；分析与包装器必须核对请求中的 `secondary_input`，不能因 schema 版本未变就把新旧路径混为一谈。

使用包装器时，构建清单完整嵌入 `request.json`，与环境快照、`telemetry.json`、stdout/stderr、`controlled-result.json` 一同保存；台架结果在同次目录的 `bench` 子目录。`artifact-snapshot` 自动保存该次实际源码、EXE、runner 和原始构建清单，避免日后只剩已改变的源码路径。必须同时检查包装器的 `environment_regime`、环境结论与台架的统计 verdict，不可只选较好的一层。测前注册和修订也随结果归档。

计算候选通过后，还须在**确实可卸载的实际工作**中验证，才能接入正式优化：

1. 单卡和双卡必须产生相同质量的用户可见结果，不能通过新增不必要的后处理制造“可卸载工作”。
2. 纳入完整输入获取、复制、格式转换、同步、辅助 GPU 到实际显示适配器的必要回传、合成与 `Present` 开销。
3. 同时检查显示帧时间、丢帧/重复帧和帧龄/延迟；流水吞吐提高不保证单帧延迟降低。
4. 固定真实场景重复 A/B，满足收益与尾部帧时间门槛，并且设备不支持、失去响应或收益消失时能回退。
5. 仅对已验证的硬件/驱动/工作负载声明支持，不扩大为“任意游戏双 GPU 加速”。

当前台架拥有自己的 DX12 命令和资源，因而可以直接移动后处理。外部捕获拿到的是游戏已完成的图像，不能撤销游戏此前已经执行的工作；现有 Pavise 主程序也没有可直接卸载的 GPU 后处理链。台架通过不授权向受保护游戏注入 DLL，更不构成反作弊安全保证。
