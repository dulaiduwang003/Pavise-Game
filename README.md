## 性能

上图是 v1.7.1 时期的四档台架测试。测试条件：i7-9750H 笔记本，后台运行微信、Clash、QQ、QQ 音乐，以干净系统为基准 100。三场景平均下来，不开 Pavise 为 59，常规模式 60，竞技模式 96。图里的常规和竞技就是现在的智能和专注，极限模式已下架。

Pavise 不产生额外性能，作用是把后台占用的那部分还给游戏。所以后台程序多、CPU 或磁盘争抢明显的机器提升明显，系统本身干净或者游戏完全卡在显卡上的，提升有限。

极限模式在高负载场景只有 71，低于竞技模式的 93，这就是它下架的原因。压制强度和性能不是正相关关系，默认预设是最温和的一档。

实际效果请在同一游戏、同一场景下自行开关对比。

## 实验功能：VidMm 显存驻留

这是已接入的可选实验策略，位于「优化策略」，默认关闭。Pavise 查询实际游戏渲染进程的显存预算与使用情况；持续出现预算压力、适配器身份明确且没有既有预留时，才尝试声明一份保守的显存需求，并回读核实结果。

它不增加或锁定显存，不安装驱动、不注入游戏。权限受限、仅核显设备、适配器不明确或写入无法确认时会跳过或停止尝试；混合显卡的实际渲染路径仍需实机验证。退局撤销本工具的预留，无法完成恢复时保留恢复记录。

这不是普遍提帧保证。实际收益和驱动兼容性仍需同场景实机对比；接口调用成功不等于游戏更流畅。

## 使用

把游戏的 EXE 或快捷方式加入目标库，也可以用扫描功能导入已安装的 Steam / Epic / GOG / 育碧 / Riot / WeGame / 战网 / Xbox 游戏。

游戏运行期间自动保护，切换到桌面或最小化不会失效。通过启动器启动的游戏（如英雄联盟）首次确认后会记住游戏本体，下次直接识别。启动器、更新器、崩溃上报和反作弊进程不会被识别为游戏。

游戏退出时按记录恢复可恢复的会话临时改动；Pavise 异常退出后，下次启动继续尝试，失败时保留恢复记录。应用显卡偏好持续保留，英文切换不回退，已清理的缓存不能恢复。

## 模式

| 模式 | 压制范围 |
|---|---|
| 智能 | 对局一开始就把通过保护边界的后台一次性隔离到底，不看热度也不逐级爬。你正在用的程序和它的家族始终不动 |
| 专注 | 隔离范围扩大到游戏之外的全体，有窗口的也不例外，切出游戏后用的程序照降，只有白名单例外 |
| 自定义 | 后台压制、核心、内存电源、系统环境、显卡逐项自选 |

两档的差别不在压制强度，只在哪些进程有资格被碰：通过边界的一律直接隔离，冷进程也压，不等它先吃十几秒资源才动手。隔离档写入的是最低优先级、最低磁盘 IO 和分页优先级、EcoQoS 与定时器精度封顶、关闭睿频提升，开了 GPU 让位再加显卡调度优先级降到最低。

这与 1.9 时期的做法相反，因为前提变了。当时全员隔离确实是负优化——上百个空闲进程的零散唤醒被亲和性收缩挤进两个核互相排队，最长帧翻 2.6 倍。2.0 起后台一律不改亲和性，收缩和移核整套下架，冷进程没有就绪线程时本来就不耗 CPU，偶尔醒来也能在任何一个没有更高优先级工作的核上跑，不再排队，全员隔离的代价随之消失。

任何模式下，反作弊、Windows 核心服务、网游加速器、输入音频与外设链、硬件控制工具和其它登录账户都不会被压制。这条边界不受任何开关影响。

游戏家族豁免默认开启：游戏平台、启动器外壳、游戏目录下的常驻进程和游戏派生的子进程都会整族放行。手动关闭后，才会只放行游戏本体和白名单，其余按普通后台压制。
## 逐游戏独立配置

游戏库里选中游戏点独立配置即可进入，每个游戏可以单独覆盖模式、后台压制、核心、内存电源、系统环境和显卡策略。没覆盖的项跟随全局，改动立即保存，大部分在该游戏下一局生效。

- 大部分逐游戏配置在对局激活时确定，下一局应用改动；暂停非必要服务和禁止 CPU 空闲的开关会在当前会话中处理，关闭后撤销本次修改
- 当前的核心选择可以锁定给某个游戏，其它游戏不受影响
- 一套覆盖可以一键清回全局
- 概览页和托盘显示当前实际生效的模式，来自哪个游戏的独立配置会标注出来
- 驱动写入连续失败自动关闭对应开关时，该游戏的这条覆盖一并清除

游戏条目支持重命名，只改显示名称，识别不受影响。

## 功能

**进程和核心**

- 游戏进程获得高优先级、更高的磁盘 IO 和显卡调度优先级以及独立核心，后台按模式降级。后台不改亲和性，不做核心收缩也不迁移
- CPU 分区适配混合架构、X3D 和多处理器组。6 核及以下不做核心切分
- 核心分配可以逐核手动划，预设有全核、关超线程、仅性能核和反选，改完要点应用才算数。多数人不需要动它，系统调度器默认就把游戏线程放 P 核
- 智能保帧：识别决定帧率的关键线程单独提升。台架实测 CPU 满载时 1% 最差帧改善 77%~96%
- 智能让位：CPU 持续吃满十秒且帧线程未能单独接管时，游戏本体暂回普通优先级，实测该状态下整进程高优先级恶化尾部帧。帧线程接管成功或 CPU 空出即恢复高优先级
- 对局自让位：Pavise 自己让出游戏核心并降低调度权重
- 反作弊相容名单：被拒绝写入的游戏记进名单，注定失败的优先级和 IO 不再重试，显卡调度优先级和帧线程照常尝试。换版本自动失效，反作弊页可查看和清空

**显卡**

- 显卡页分为「通用 / NVIDIA / AMD / Intel」。通用页的「应用显卡偏好」可从 EXE 或正在运行的应用中选择后台程序，保存 Windows 节能显卡偏好。仅确认同时存在核显与独显时允许新增，不把 Intel Arc B580 当成核显。[下次启动应用生效](https://support.microsoft.com/en-US/Windows/Hardware/Display-Graphics/optimizations-for-windowed-games-in-windows-11)，不迁移或重启正在运行的程序，也不保证游戏独占独显。偏好持续保留，退局和退出 Pavise 不撤销；移除条目或清除全部配置时只还原本工具的修改，保留原有节能设置及检测到的外部更改。无法确认写入或恢复结果时保留记录，不强行覆盖
- Intel 页提供「游戏期间 Intel 全局低延迟」，默认关闭，开启前说明全局作用范围，也可逐游戏覆盖是否启用。仅在官方 IGCL 明确提供实时切换能力的 DX9/DX11 路径上启用基本 On；不启用 Boost、XeSS 补帧、超频或限帧。不保证提高帧率；多显卡机器也只修改选定的 Intel 适配器，不保证它就是游戏正在使用的显卡。原本已 On/Boost 时跳过，退局仅还原可确认归属的本次修改；未确认的写入不获得恢复权。实际可用性取决于驱动报告的能力，参见 [Intel IGCL 接口定义](https://github.com/intel/drivers.gpu.control-library/blob/b6c462933502e13d1537dd5024949a51be30e63d/include/igcl_api.h)
- 后台 GPU 让位：后台进程使用显卡时，同步降低其 GPU 调度优先级
- NVIDIA 逐游戏调优：电源最高性能、低延迟模式（开或超级）、Smooth Motion 驱动插帧、着色器缓存放开、DLSS 覆写（最新或指定 J、K 代）、按游戏开启 ReBAR。原值有快照，关闭即恢复
- 显卡功耗墙：对局中拉到厂商允许的上限，退局按快照还原

**键鼠和中断**

- 进入游戏切英文一次：位于「优化策略 → 会话附加」，默认关闭，可逐游戏覆盖。只在入场短窗口内向实际前台游戏尝试一次可用的独立英文键盘布局；用户随后切中文、切出返回都不再干预，退局不恢复输入法。游戏中途开启留到下次启动生效，重启 Pavise 不补切已经运行的游戏。使用 [Windows 输入语言请求](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchangerequest)，不模拟按键、不改默认输入法、不改系统布局共享方式；不依赖某一家中文输入法，但缺少可用英文布局、权限受限或游戏拒绝时跳过，不能保证所有第三方输入法与游戏都响应
- 关闭筛选键、粘滞键和切换键。微软对这几项的定义就是忽略短促击键，开着必然有延迟
- 禁止系统挂起键鼠设备，治的是空闲一会儿之后第一下操作发飘。只碰键鼠，不碰 U 盘和声卡
- 修复其它工具改动过的输入队列长度，关闭指针精度增强（系统那条鼠标加速曲线）
- 前台时间片三档自选：系统默认、前台加权、只报告。前台加权是老优化圈那个 0x26，依机型，台架上并非稳赢，选完请自己在同一场景对比；其它偏方值一律按异常报告
- 显卡中断亲和挪到靠近渲染线程的核心。USB 和硬盘控制器的中断亲和已在 1.8.1.0 下架，理由见下文

**内存和电源**

- 对局默认切到 Pavise 托管电源方案，首次对局自动创建，各项参数按本机处理器写入，名称带 PG 标签和本机签名；也可改选本机任意计划，Pavise 只负责切换不改其参数。设一次即不再定时轮询，避免与其它电源软件反复抢方案
- 托管方案按档位分两套。专注档写最低性能状态 100%、不停泊核心、能效偏好最偏性能、Boost 策略拉满；智能档保留降频余量，台式机上能效偏好同样写最偏性能并关掉插电时的占空比调制，笔记本给折中值
- 禁止 CPU 空闲：位于「优化策略 → 会话附加」，默认关闭，每次开启先警告确认。仅在游戏中、确认交流供电且使用 Pavise 托管电源方案时尝试生效，只改 AC 值；关闭、退场或拔电后恢复本次修改，不写用户自选方案。可能增加功耗、发热和风扇噪声，部分平台反而降频或掉帧。收益需自行对比，不做自动提帧判定
- 待机内存清理（ISLC 规则）：位于「优化策略 → 会话附加」，默认关闭、开启前确认。列表大小和真正空闲内存同时达到用户阈值才清理整个待机列表；参数全局共享，开关可逐游戏覆盖。不会裁剪游戏或后台工作集，详见下文
- 功耗让路：笔记本上 CPU 和 GPU 吃同一份功耗与散热预算，GPU 撞墙而 CPU 有余量时，把能效偏好放到偏性能一侧的中间值，让预算流向 GPU。默认关闭，仅笔记本、插电、专注档、Pavise 托管电源方案且能读到 RAPL 瓦数时才参与，一局只决定一次。观察 20 秒决定，engage 后再验 15 秒，让不出至少 3W 或 GPU 利用率掉超过 3% 就立刻退回并停止自动尝试；满足条件后，只有用户确认重新开启才会重试。作者本机 i7-9750H 实测 EPP 全量程对封装功耗和实际频率毫无作用，这类机器上必然验不过——那正是预期行为
- MMCSS 多媒体调度：非多媒体工作的预留份额从 20% 调到 10%，Games 任务的调度类别和文件 IO 提到高档。游戏模式开启期间常驻，关掉或退出即还原
- Game DVR 后台录制在游戏模式开启期间关闭、退出 Pavise 才还原，因为它由系统在游戏启动那一刻读取，必须先于游戏就位才生效
- 电源计划、网络、通知在游戏结束后全部恢复

**系统环境**

需要重启、或者会留在机器上的改动集中在这一页，每一项都可还原：

- 硬件加速 GPU 调度（HAGS）。它对平均帧的影响在误差内，意义是驱动帧生成一类功能的前置条件，关着就用不了。不支持的机器置灰
- 关闭 VBS 虚拟化安全，开启前有风险确认
- 卸载 CPU 推测执行漏洞的软件缓解，回收每次内核态切换的固定开销。只有确实测到可回收开销的机器才放开
- 游戏模式守护、窗口化游戏优化、设备电源

**看得见的部分**

- 系统体检页：只读检查本机能力，每条结论标注依据等级。检出被第三方改坏的系统项可以就地一键修复，可查看显卡当前受功耗墙或温度墙限制的状态。中断那一行用内核 ETW 抓 DPC 和 ISR，直接点名头号来源
- 会话报告：游戏时长、压制的进程数量及其 CPU 占用、受功耗墙和温度墙限制的时间占比，以及游戏溢出到系统内存的共享显存峰值
- 游戏库支持强制接管，模拟器、云游戏这类识别不出来的，进程一起来就进对局
- 白名单独立成页，拖入即可，作用范围自动判断

纯本地工具，不安装服务、不上传数据、不注入游戏进程、不修改游戏内存和文件。每一步写入尽量读回核对，读不到预期值不计为成功。

## 内存清理

**当前可选：待机内存清理（ISLC 规则），默认关闭。** 在「优化策略 → 会话附加」开启，旁边的「设置参数」统一保存三项参数：列表大小阈值、空闲内存阈值、检测间隔。默认分别为 1024 MB、1024 MB、4000 ms；MB 按 1024² 字节计算，范围为 0～1048576 MB，间隔范围 250～300000 ms。这是 Pavise 的默认配置，不宣称与每版 ISLC 的出厂设置相同。

判定为 `List ≥ 列表阈值 AND Free < 空闲阈值`。List 使用待机列表加系统工作集的计数；Free 只统计 Free + Zero 页，不把待机缓存计作真正空闲。任务管理器的 Available 包含待机缓存，不能代替 Free。[ISLC 作者对 Free 的说明](https://www.wagnardsoft.com/forums/viewtopic.php?p=6381)、[微软对内存计数的定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)。

仅在检测到游戏会话时轮询，操作为 `MemoryPurgeStandbyList`，清理全部优先级的待机页，不清系统或进程工作集、不刷新修改页、不合并内存页、不更改内存压缩、页面文件或定时器精度。轮询使用独立线程，不重叠执行、不补发积压检测，也没有隐藏的额外冷却。连续两次读取或清理失败会关闭策略，重新开启需再次确认。

关闭当前游戏生效的清理策略、退出游戏或退出 Pavise 会撤销尚未开始的清理；已进入 Windows 的调用无法中断，停机须等待其结束，已丢弃的缓存无法还原。全局开关是默认值，逐游戏强制开启优先于全局关闭；要停止该游戏的清理，请关闭它的独立配置或游戏守护总开关。清理可能增加磁盘读取、加载时间或短暂卡顿，不能保证提升帧率或所有环境零风险；不建议和另一个自动内存清理器同时开启。阈值和间隔共享全局参数。这里实现的是 ISLC 的核心内存规则，不包含它的独立启动管理、排除列表界面及可选定时器功能。

**以下保留旧实现的测量记录，不是本次新策略的性能测试结论。**

下表逐条测量了这类工具会用到的系统级命令，测试机 64 GB 内存，测量前可用 40344 MB、系统缓存 16154 MB：

| 命令 | 耗时 | 可用内存 | 系统缓存 |
|---|---|---|---|
| 清空所有进程工作集 | 1894.9 ms | +5191 MB | +3364 MB |
| 清待机列表（低优先级） | 13.3 ms | +144 MB | −47 MB |
| 清待机列表（全部） | 1380.6 ms | +382 MB | −18894 MB |
| 刷新修改页列表 | 8019.7 ms | +5845 MB | +251 MB |
| 合并物理内存页 | 6152.1 ms | +2121 MB | +531 MB |

清空整个待机列表丢掉 18894 MB 系统缓存，只换来 382 MB 可用内存。待机列表本来就计入可用内存，清空它是把缓存着的可用内存变成空着的可用内存，总量几乎不变，而缓存内容不再保留，紧接着的游戏加载要重新读盘。刷新修改页列表耗时 8 秒、合并物理内存页 6.2 秒，都不适合放在开局路径上。

**已移除：内存吃紧时清理低优先级待机内存**

这一项曾被当成"吸取教训后的保留版"，2026-08-20 实测证明它栽的是同一个坑，只是更隐蔽。

触发条件用的是可用内存比例，而可用内存本来就把待机页算在内——清理只是把页从待机链表挪到空闲链表，这个比例不会变，于是条件永远解除不了，45 秒冷却只是给无限重复定了个节拍。真实用户日志里 10 分钟触发 14 次，间隔精确 45 秒，从没停过。

更关键的是它几乎什么都没做：`MemoryPurgeLowPriorityStandbyList` 只清优先级 0 那一档，24GB 机器上那一档总共 1.4 MB，单次实际释放 0.0 至 0.1 MB，调用耗时 0.2 毫秒。省下的是内存管理器几百纳秒的页回收开销，对一帧的预算是噪声。

**已移除：对局稳定后回收后台工作集**

逐个调用 `SetProcessWorkingSetSize` 并不释放内存，只是把页从工作集赶到待机列表，其中的脏页还要先写进页面文件——这笔磁盘 IO 恰好落在对局中。而目标本身是已被压制的后台进程，正是内存管理器在有压力时首批自然裁剪的对象；它们没有被挂起，裁完立刻缺页读回，几秒后这轮工作就白做了，净效果是对局中多出一轮读写。

**已移除：旧版基于 Available 的整个待机列表清理**

旧实现按 `待机列表 ≥ 1 GB 且可用内存 ≤ 1 GB` 每 5 秒判定，使用 Available 而非 ISLC 的 Free，不能代表 ISLC 的实际触发行为。上述历史测量中，完整待机清理单次调用耗时约 1380 ms，系统缓存减少约 18894 MB，Available 仅增加约 382 MB。该版本和低优先级版本均已下架；新增策略采用真正的 Free 双阈值，但清理缓存可能带来额外读取的代价仍然存在，不能把“调用成功”当作“游戏更流畅”。

相关论述见 Mark Russinovich《The Memory-Optimization Hoax》（Windows and .NET Magazine，2004 年 1 月）。

## 不做的事

流传的键鼠注册表优化项大多作用在零点几毫秒的量级上，而延迟的主要来源是渲染队列。这类项目 Pavise 只报告不修改，包括蓝牙鼠标和 125 Hz 回报率——体检页会把它们点出来，改不改由你自己决定。

MSI 模式、低延迟模式、后台硬限帧、游戏文件预热和按位置屏蔽 CPU 0/1 都实现过并已移除，原因分别是实测无效、有写坏设备的风险，以及语义理解错误——驱动中的后台限帧实际作用于失去焦点的应用，切出游戏后被限制的是游戏本身。

驱动级帧率上限（NVIDIA 与 AMD）在 1.8.0.3 下架：限帧交给游戏内设置或显卡控制面板更直接，驱动层再限一次容易与游戏自身的限帧和 VRR 打架；AMD 侧还要借道 Radeon Chill，与 Anti-Lag 互斥，等于用一个延迟优化换另一个。

1.8.1.0 收回三项：USB 与硬盘控制器的中断亲和，在性能核少的混合架构上会把中断投到低频能效核，造成高回报率鼠标空闲后第一下发飘；独立的对局核心解停泊覆盖，与托管电源方案里的停泊设置重复；逐游戏强制独显偏好，现代 Windows 本就默认给游戏挑独显。靠近渲染核的显卡中断亲和保留。

竞技档自动禁用处理器空闲同版收回。现在是默认关闭、开启前必须确认风险的手动策略，不由预设自动启用，也不运行旧版的频率压测。

极限模式和英雄联盟游戏专栏在 1.8.0.2 下架，专注即最高档。

后备提优（IFEO）和逐游戏关闭 CFG 已移除，包括全局与逐游戏入口、启动预置和对局写入。不做旧字段兼容；游戏库仍含已移除的逐游戏字段时，按现有不兼容处理流程还原系统改动、自动清除旧数据、弹窗并退出。清理失败会保留恢复记录并说明原因。

移除的项目仍然保留历史改动的恢复能力。正常启动和版本更新不主动恢复，使用设置页的清除按钮撤销；若游戏库不兼容或读写失败，则走上述自动清理退出流程。

## 运行和数据位置

双击 `Pavise.exe` 后进入托盘。程序未数字签名，SmartScreen 可能拦截提示，选择仍要运行即可。调整其它进程需要管理员权限。开机启动通过计划任务实现。启动时向官方更新源检查一次版本，不上传本机数据。

数据默认保存在 `%AppData%\Pavise`，包括目标配置、白名单和运行日志；界面和功能开关保存在注册表 `HKCU\Software\Pavise`。在程序旁放置空文件 `Pavise.portable` 后改为保存在程序目录。

设置页提供一键恢复。
