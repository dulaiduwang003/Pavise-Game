# 线程巡检与恢复开销对照

## 实验方法

2026-11-07 使用相同的自有休眠子进程，在 154 个已采样线程的规模上，对比修改前后的稳定巡检和恢复结算。台架使用真实原生读回及生产持久化存储，核对原掩码恢复；不启动游戏，不改变全局 CPU 预留。

优化主要合并同一轮已经取得的核验信息、按线程 ID 与创建时间定位记录，以及减少已经完成的恢复结算。修改前写入原值、持久化恢复意图、应用时重新核实拓扑和动态范围等约束保持不变。

## 稳定巡检

每个对照先预热 5 轮，再测量 100 轮。计时包括原生会话及持久化恢复存储，不包括进程快照采集、独立守护与全局隔离。154 个线程的对照汇总如下：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 每轮原生读取次数 | 307 | 154 |
| 每轮耗时中位数，毫秒 | 47.1951 | 9.4322 |
| 每轮耗时 P95，毫秒 | 62.9179 | 11.7397 |
| 稳态线程写入 | 0 | 0 |
| 稳态恢复记录保存 | 0 | 0 |

## 初次应用与退出结算

另一组相同规模的自有线程实验使用真实持久化存储：

| 阶段与指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 初次应用保存次数 | 462 | 309 |
| 初次应用耗时，毫秒 | 2277.4516 | 1525.4752 |
| 已退出进程结算保存次数 | 154 | 1 |
| 已退出进程结算耗时，毫秒 | 1158.8044 | 9.1893 |

修改后的退出结算没有继续读写目标线程，重复结算没有再次保存。减少的是取得明确退出证据后的重复工作；查询失败或身份未知仍保留恢复债务。崩溃边界使用隔离夹具中的持久化前缀重放验证，该部分没有实际杀死进程。

[汇总数据](data/runtime-overhead-20261107.csv)逐项保存原始数值和单位；[样本身份](data/README.md)区分两组开发快照。原始摘要没有完整记录 CPU、驱动和温度条件，因此这些耗时只代表该次运行，不作为跨设备固定值。后续源码整理没有重新产生这组历史耗时。

## 如何复核

当前实现可从 `CriticalThreadHardAffinitySession.*.cs`、[HardThreadJournal.cs](../../src/PaviseApp/HardThreadJournal.cs) 和 [GameMode.Recovery.cs](../../src/PaviseApp/GameMode.Recovery.cs) 检查。公开的恢复回归核对所有权、有限重试和结算边界，入口见[恢复验证](recovery.md)。

重新测量时，应保持线程数量、原生查询路径、存储介质、构建优化选项和输入范围一致，分别报告预热、轮次与离群处理；同时核对原值恢复和全局配置未变。

这些结果衡量 Pavise 自身的巡检与恢复工作，不是游戏 FPS 或输入延迟结果。
