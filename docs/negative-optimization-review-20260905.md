## 1. [P2] 整机饱和守卫漏掉局部核心上的优先级倒置

位置：`src/Core/GameMode.Boost.cs:254,267,276`、`src/Platform/CpuSaturation.cs:10,65`。

`EffectiveGameMask` 能选择局部掩码，但饱和判定只读取 `GetSystemTimes` 的整机利用率，超过 90% 持续十秒才降到 Normal。它不接收游戏允许的核心集合，也不判断跨进程依赖。因此“只占满一个核、整机仍很空闲”不会被这道保护识别。

### 实测方法与结果

两个自建进程通过共享内存请求/应答：等待方主动忙等，协作者每次执行固定 CPU 工作再应答。协作者始终 Normal；等待方比较 Normal 和当前生产 `BoostPriorityTarget(false, false)` 返回的 High。两个进程使用相同逻辑 CPU 2，另设 CPU 2 / CPU 4 分开的对照。每种布局按 A-B-B-A 重复两组，每臂两秒；没有启用 RenderLane、运行整个 Boost/Sweep、修改用户进程或将线程设为实时优先级。

最终整轮结果：

| 布局 / 等待方优先级 | 臂数 | 两秒内完成协作次数范围 | 中位数 |
|---|---:|---:|---:|
| 同逻辑核 / Normal | 4 | 52–61 | 55.5 |
| 同逻辑核 / High | 4 | 0–0 | 0 |
| 分逻辑核 / Normal | 4 | 66,348–66,686 | 66,446 |
| 分逻辑核 / High | 4 | 66,521–66,804 | 66,647 |

同核 High 四臂中，协作者 CPU 时间均为 0，等待方约消耗 1,984–2,000 ms CPU，整机利用率约 4.70%–5.37%。第一轮同样四个 High 窗口均无协作完成，Normal 为 45–60 次。所有自建进程亲和及优先级均已回读、恢复并退出。

零完成窗口的 p50/p95 保留为 NaN；**不能编造为“游戏帧时间两秒”或“永久死锁”**。这里刻意使用跨进程忙等和同核限制，并未证明某款游戏正采用该模式。分核对照没有停顿，微小完成次数差异不作为收益结论。微软也明确提醒高优先级等待低优先级线程时应阻塞而非忙等：[Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)。

影响与建议：存在硬限制/局部争用及协作者依赖时，High 不是“整机未饱和即可放心开启”。应评估掩码内负载，并对未验证的跨进程依赖保持保守；不应再用“CPU 总占用低”证明提权安全。此结果不足以要求所有游戏无条件删掉提优，也不能仅把 High 换成 AboveNormal 就宣称问题已解决。

## 2. [P2] 功耗让路把不可用 CPU 读数带入决策

位置：`src/Core/Suppression/PowerBudgetYield.cs:195,213,242,495,551`、`src/Platform/CpuSaturation.cs:65`。

直接运行生产 `PowerBudgetYield` 状态机；GPU 98%→97%、封装功耗 45 W→41 W、有效 CPU 利用率 40% 为合成值。每种输入序列重复五次，使用模拟时间推进，不改真实 EPP、不调用笔记本运行器的硬件写入。

| 输入序列 | 五次结果 | 含义 |
|---|---|---|
| CPU 全程有效的对照 | 5/5 Engage 后 Keep | 对照策略正常推进 |
| 首个 CPU 样本取真实新建 `CpuSaturation.Sample()` | 5/5 首次 NaN，观察结束 Skipped | 第一个缺测污染均值，后续有效样本无法修复 |
| 观察期有效，验证期 CPU 全部 NaN | 5/5 Keep / Kept | CPU 负载漂移没有证据，仍被接受 |

第一种异常不只是人为造数：新建 `CpuSaturation` 第一次没有时间差，必然返回 NaN。运行器在首轮 GPU 数据有效时会将其传入状态机；`cpuSum` 变成 NaN，观察期判据失败。本例是**功能可能失效**，不是实测 FPS 负优化。

第二种异常更应优先修复：`Math.Abs(NaN) > MaxCpuUtilShift` 为 false，缺失 CPU 证据等于绕过负载漂移守卫，仍允许保留让路。它是可能保留错误功耗限制的路径，但本机没有实测让路后的游戏损失。

同时静态检查发现：`PowerBudgetYield.cs:560` 在 GPU 读数小于零时直接 continue，虽有重开采样器，却没有有效样本超时撤销；已让路后连续缺测可能一直保留到关闭/退局。这个子项本轮没有完整运行器故障注入验证，不能算已在真实电源计划上复现。

建议：预热 CPU 差分采样；有限且范围有效的样本才进入各自分母；缺测不能通过验证；为已施加状态增加按时间计算的证据失效撤回。之后用运行器级模拟写入测试覆盖连续缺测、恢复失败和退出边界。

## 3. [P2] 自动核显分配的可见性保护粒度不匹配

位置：`src/Core/GameMode.AutoGpuPreference.cs:79,90,101,116,158,179`、`src/Core/Tweaks/AppGpuPreferences.cs:37,209`。

可见窗口集合只有 PID，过滤时只查 `visible.Contains(candidatePid)`；但最终显卡偏好按 EXE 路径保存。若可见主进程与无窗口 GPU 辅助进程使用同一个 EXE，辅助进程可通过 PID 检查，登记的却是整个路径。随后启动该 EXE 的可见进程也可能受省电偏好影响；这不是立即迁移已经运行的 GPU 进程。

聚焦组合探针设置可见 PID=1001、同 EXE 的无窗口候选 PID=1002，明确假设其有 GPU 活动、硬件支持且不在游戏库/白名单中。可见 PID 的集合检查按调用方原表达式执行，其后调用真实 `AutoGpuEligible` 和 `AutoGpuEnroll`，偏好控制与账本完全模拟：

- 直接选择可见 PID 的对照：5/5 跳过，模拟偏好不变。
- 选择同 EXE 无窗口候选：5/5 成功登记 `GpuPreference=1`。

**这是过滤器组合与模拟持久化测试，不是完整窗口/GPU/身份发现循环，也没有实测浏览器或游戏跨卡性能。** 可见性与写入粒度不匹配由调用点代码确认；真实掉帧与发生率尚不可知。极限模式的 `autoecogpu` 会请求此路径，仍须满足真实混合显卡支持等门槛。

建议：按可见应用的规范化 EXE 路径保护，并考虑可验证的可见应用家族，防止同路径子进程绕过；`EnumWindows` 的返回值也必须检查，失败时不能把不完整集合当作“没有窗口”。保留“不覆盖既有显卡偏好”的现有保护。修复前应限制自动登记，不应因此删除用户显式选择显卡的手动能力。

## 4. [P3] 首次共享显存查询阻塞扫描线程；已有快照复用有实际价值

位置：`src/Core/Detection/VramSpillProbe.cs:24,34,58`、`src/Core/GameMode.Lifecycle.cs:241,247`、`src/Platform/ProcessSnapshot.cs:124`。

只读调用生产方法。四个独立台架进程的首次共享显存 PDH 查询耗时分别为 384.18、188.43、190.65、193.11 ms；最终进程后续七次查询中位数 0.2164 ms，最大 0.2474 ms。首次值包含冷启动/JIT/提供者初始化，不归因于某一个内部函数；不能把第一笔复制成每二十秒都必然发生。

生产路径每二十秒最多采一次，直接在 Pavise 扫描线程上执行，先于 Sweep/Boost。应考虑后台执行或复用持久查询，减少首轮控制动作的阻塞。**这不是渲染线程停顿，也不是测得 193 ms 游戏长帧。** 完整产品中其他 PDH 使用可能已预热提供者，独立进程冷路径不等于每局首次必然一样。

最终台架约 670 个进程：强制新快照首笔 34.10 ms，后续十一笔中位数 13.58 ms；立即复用现有快照的中位数约 0.0006 ms、零新路径查询。如此短的调用只解释量级，不宣称亚微秒精确性。结果支持保留现有事件驱动/快照复用机制，不支持改成每轮强制重扫。这些是本进程墙钟耗时，不能当整机 CPU 百分比或 FPS 降幅。

## 修复与验收

修复日期：2026-09-05，Asia/Shanghai。四项改动限于已定位路径，没有增加定时电源计划巡检，也没有恢复缓存预热。

1. **受限核域的 High 准入。** 自定义/严格/默认掩码只要不是完整核域就使用 Normal；多处理器组或核域不明同样保守处理。在首次写入及既有回读审计时检查实际进程 affinity / CPU Sets，受限或无法读取则本局保持 Normal。同步撤销候选线程提优、拒绝迟到晋升；恢复成功后不再每轮扫描重读线程恢复账本，失败仍保留重试与退局恢复。完整核域且通过既有饱和检查的场景保留 High，不增加逐核 PDH 轮询。
2. **功耗缺测保护。** CPU 差分采样先预热；CPU/GPU 必须为有限的 0–100% 才进入负载均值，瓦数/频率只接受有限正值。首个 NaN 不再污染后续样本。让路验证期连续缺少完整证据，或保持期缺少有效 CPU/GPU，达到 10 秒后在下一次采样推进时发出撤回；恢复失败保留底层恢复记录，不伪报已恢复。缺测结论是 Inconclusive，不熔断硬件。观察期一直没有证据最迟 60 秒放弃。本轮还将样本处理与真实运行器的写入分发合并，使故障注入覆盖到撤回委托，而不只测试状态枚举。
3. **自动核显的路径级保护。** 可见程序以及有创建时间/会话依据的后代按规范化 EXE 路径保护，隐藏的同 EXE 子进程不能绕过。窗口枚举失败、相关可见身份/路径不全时拒绝自动登记。Prepare 后、Apply 前重新捕获候选身份、进程快照、窗口集合和游戏库保护状态。人工显卡选择与“不覆盖既有偏好”的行为不变。
4. **共享显存查询后台化。** 扫描侧只复制 PID 集合并提交一次后台任务；显卡清单初始化与 PDH 都在工作线程。保留 20 秒限频，旧任务未完成时不叠加查询；重置/封存/关闭通过代际令牌拒绝迟到结果，关闭有界排空。队列失败、原生查询异常及无效数值均不会阻断扫描流程。

### 边界与取舍

- Normal 是对受限域的保守策略收紧，不是证明所有游戏使用 High 都有害，也不是证明保留 High 的其他场景必然获益。现有约 20–30 秒审计节流保留，不能保证外部刚改 affinity 就立即发现；未检查任意线程内部亲和或所有跨进程依赖。
- 功耗的 10 秒按有效样本时间判断，实际撤回还取决于下一次采样调用返回及原生恢复成功，不是独立实时 watchdog。没有在本机伪装共享功耗笔记本，也没有实写 EPP。频率代理仍不是 FPS 收益证明。
- 窗口集合与注册表不可能在此实现中原子提交，最后检查之后出现窗口的极小竞态仍存在；保守的路径/家族保护也可能少登记一些真正后台应用。本轮不撤销用户已有显卡偏好。
- 显存查询成本移到后台，不是消除查询成本，不是测得某一游戏长帧缩短。原生查询异常卡住时只保留一个在途只读任务，关闭超时不伪报已排空。
